# 음성 기록 자동 문서화 시스템 단계별 개발 로드맵

> 상태: 실행 로드맵 초안 1.0
> 요구사항 기준: `docs/00_first_destination.md`
> 설계 기준: `docs/01_implementation_blueprint.md`
> 이 문서는 구현 순서와 단계별 작업·검증 게이트를 정의한다. 설계가 충돌하면 구현 설계도를 우선한다.

## 1. 로드맵의 목적

이 로드맵은 구현 설계도를 실제 개발 작업으로 전환하기 위한 실행 순서를 제공한다. 각 단계는 다음 질문에 답해야 한다.

- 무엇을 먼저 만들어야 하는가?
- 해당 작업이 의존하는 선행 작업은 무엇인가?
- 어느 정도까지 구현해야 다음 단계로 넘어갈 수 있는가?
- 자동 검증과 수동 검증은 무엇인가?
- 단계가 끝났을 때 사용자가 확인할 수 있는 결과는 무엇인가?

로드맵은 달력 기반 일정보다 의존성과 검증 게이트를 우선한다. 현재 팀 규모, 개발 장비, Linux GPU 장비 확보 시점이 정해지지 않았기 때문에 “몇 주차”로 고정하면 잘못된 약속이 된다. 단계별 작업 크기를 관리하고 각 게이트를 통과한 시점에 다음 단계로 이동한다.

## 2. 진행 원칙

### 2.1 세로로 작게 완성한다

백엔드, 프런트엔드, 모델을 각각 끝까지 만든 뒤 합치지 않는다. 먼저 가짜 모델을 사용해 아래 흐름을 브라우저까지 연결한다.

```text
fixture m4a
  -> 입력 감지
  -> DB 작업
  -> 가짜 STT/화자/분류/요약
  -> JSON/Markdown 결과
  -> FastAPI
  -> React 대시보드/상세 화면
```

이 수직 흐름이 안정된 다음 가짜 어댑터를 실제 WhisperX, pyannote, LLM 구현으로 하나씩 교체한다.

### 2.2 단계 완료는 코드 작성이 아니라 검증 통과다

각 단계는 아래 세 조건이 모두 충족되어야 완료다.

1. 단계에 정의된 산출물이 존재한다.
2. 필수 자동 검증이 통과한다.
3. 단계 종료 시나리오를 사용자가 재현할 수 있다.

코드가 작성되었어도 Compose에서 실행되지 않거나 브라우저 흐름이 끊기면 완료가 아니다.

### 2.3 실제 모델과 외부 서비스는 명시적으로 격리한다

- 일반 개발과 CI는 가짜 어댑터로 반복 가능하게 만든다.
- WhisperX/pyannote 평가는 Linux GPU 환경에서만 실행한다.
- 외부 LLM 테스트는 비용과 개인정보 전송 여부를 확인한 뒤 명시적으로 실행한다.
- 모델 평가 실패를 일반 단위 테스트의 불안정성으로 섞지 않는다.

### 2.4 데이터 손실 방지 작업은 뒤로 미루지 않는다

다음 항목은 초기 단계부터 구현한다.

- 콘텐츠 해시 기반 중복 방지
- SQLite 트랜잭션
- 결과 파일의 원자적 교체
- 원본 녹음 비변경
- revision 충돌 방지
- 실패 상태와 재시도 이력
- 설정 루트 밖 파일 접근 차단

### 2.5 작업 크기 규칙

로드맵의 작업 크기는 예상 시간이 아니라 변경 범위를 뜻한다.

| 크기 | 기준 | 처리 방식 |
|---|---|---|
| `S` | 한 책임, 한 계층 중심, 검증 하나로 설명 가능 | 그대로 구현 가능 |
| `M` | API와 UI 또는 DB와 worker처럼 두 경계를 연결 | 한 PR로 가능하되 중간 커밋을 분리 |
| `L` | 세 계층 이상 또는 검증 기준이 여러 개 | 착수 전에 `S`/`M` 작업으로 분해 |

로드맵에는 `L` 작업을 남기지 않는다. 구현 중 `L`로 커졌다면 숨겨진 요구사항이 생긴 것이므로 범위를 다시 나눈다.

## 3. 전체 단계와 마일스톤

```text
R0 준비 조건
  -> R1 실행 골격
  -> R2 DB·입력 감지
  -> R3 가짜 AI 수직 흐름
  -> R4 실제 STT·화자 분리
  -> R5 수동 화자 검토 GUI
  -> R6 화자 자동 식별
  -> R7 분류·transcript 문서
  -> R8 자동·수동 요약
  -> R9 운영 안정화
  -> R10 실제 환경 인수·첫 릴리스
```

| 단계 | 마일스톤 | 사용자에게 보이는 결과 | 설계도 대응 |
|---|---|---|---|
| R0 | 개발 준비 완료 | 실행에 필요한 결정과 fixture가 준비됨 | 구현 전 준비 |
| R1 | M0 실행 골격 | 브라우저에서 서비스 상태 확인 | 0단계 |
| R2 | M0.5 안전한 입력 등록 | m4a가 중복 없이 작업 목록에 등록됨 | 1단계 |
| R3 | M1 가짜 AI 수직 흐름 | 대시보드에서 가짜 transcript·요약 확인 | 2단계 |
| R4 | M2 실제 전사 | 실제 녹음에서 시간·임시 화자 포함 transcript 생성 | 3단계 |
| R5 | M3 수동 화자 MVP | 음성을 듣고 화자를 정의·수정 가능 | 4단계 |
| R6 | M4 화자 추천 | 고신뢰 기존 화자를 자동 연결하고 근거 표시 | 5단계 |
| R7 | M5 분류 문서 | 대분류와 읽을 수 있는 transcript 문서 생성 | 6단계 |
| R8 | M6 요약 문서 | 정책/요청에 따라 범주별 요약 생성 | 7단계 |
| R9 | M7 릴리스 후보 | 실패 복구·접근성·백업·E2E 완료 | 8단계 |
| R10 | M8 첫 운영 릴리스 | Syncthing부터 요약까지 실환경에서 완료 | 9단계 |

### 3.1 핵심 경로

반드시 순서대로 진행해야 하는 핵심 경로는 다음과 같다.

```text
설정/Compose
  -> DB와 job
  -> 입력 해시/멱등성
  -> 상태 전이와 artifact
  -> 실제 STT/diarization
  -> 수동 화자 확정
  -> 분류
  -> 요약
  -> 운영 인수
```

프런트엔드 컴포넌트와 실제 모델 연동은 일부 병행할 수 있지만, 각각 API 계약과 정규화된 transcript schema가 확정된 뒤 진행해야 한다.

## 4. R0 — 개발 준비 조건

### 목표

코드를 만들기 전에 작업을 실제로 막을 수 있는 환경·데이터·개인정보 조건을 확인한다. 미래의 모든 운영 결정을 확정하는 단계가 아니라, R1~R4를 진행할 최소 조건만 준비한다.

### 작업 목록

#### R0-01 개발 명령 진입점 결정 (`S`)

- Python과 프런트엔드의 패키지 관리 도구를 각각 하나만 선택한다.
- 루트에서는 `Makefile`처럼 하나의 진입점으로 설계도에 정의된 검증 명령을 호출하게 한다.
- 버전 lockfile을 커밋한다.
- 같은 기능의 shell script와 task runner를 중복해서 만들지 않는다.

**완료 증거**

- 빈 프로젝트 상태에서도 `check-format`, `lint`, `typecheck`, `test` 명령 이름이 예약되어 있다.
- 신규 개발자가 README 한 곳만 보고 명령을 찾을 수 있다.

#### R0-02 비민감 테스트 fixture 준비 (`S`)

- FFmpeg로 생성한 짧은 무음 또는 합성 음성 m4a를 저장소용 fixture로 준비한다.
- 가짜 transcript, 두 임시 화자, 분류, 요약의 기대 JSON을 준비한다.
- 실제 사람 음성은 동의와 보관 정책 없이 Git에 넣지 않는다.

**완료 증거**

- CI에서 외부 네트워크와 GPU 없이 사용할 수 있는 fixture가 있다.
- fixture의 출처와 사용 목적이 기록되어 있다.

#### R0-03 실제 모델 검증 환경 확인 (`S`)

- Linux GPU 장비와 NVIDIA Container Toolkit 사용 가능 여부를 확인한다.
- `large-v3` 모델 저장 공간과 VRAM 제약을 확인한다.
- pyannote 모델 접근 조건과 `HF_TOKEN` 준비 주체를 확인한다.
- 환경이 아직 없더라도 R1~R3는 진행하고, R4의 진입 조건만 미충족으로 표시한다.

**완료 증거**

- 실제 모델 검증을 실행할 장비 또는 명확한 미확보 상태가 기록되어 있다.
- 토큰을 저장소에 넣지 않는 전달 방식이 정해져 있다.

#### R0-04 개인정보 경로 결정 (`S`)

- 분류/요약을 로컬 LLM으로 할지 외부 API로 할지 현재 방향을 기록한다.
- 외부 API 후보라면 transcript 외부 전송 사실을 명시한다.
- 최종 공급자 결정이 늦어져도 R7 전까지 가짜 어댑터로 진행한다.

**완료 증거**

- “로컬만 허용”, “외부 전송 허용”, “미결정” 중 현재 상태가 명확하다.

### R0 종료 게이트

- [x] 단일 개발 명령 체계가 정해졌다.
- [x] 비민감 fixture와 기대 결과를 사용할 수 있다.
- [x] GPU 환경의 확보 여부가 명확하다.
- [x] pyannote 토큰과 LLM 개인정보 경로의 소유자가 정해졌다.
- [x] 미결정 항목이 어느 단계까지 결정되어야 하는지 기록되었다.

## 5. R1 — 프로젝트 실행 골격

### 목표

`web`, `api`, `worker`가 같은 설정을 사용해 Compose에서 시작되고, 브라우저에서 백엔드 readiness를 확인할 수 있게 한다.

### 선행조건

- R0 종료 게이트 통과

### 작업 목록

#### R1-01 Python 백엔드 골격 (`S`)

- `backend/app` 패키지와 `pyproject.toml`을 만든다.
- 설정 로더가 `.env`와 프로세스 환경 변수를 읽게 한다.
- 필수 경로와 범주 설정을 시작 시 검증한다.
- 구조화 stdout 로그의 최소 형식을 만든다.

**검증**

- 필수 변수가 없을 때 변수명을 포함한 오류가 발생한다.
- 유효한 임시 경로에서는 설정 객체가 생성된다.
- 비밀값이 설정 출력과 로그에 나타나지 않는다.

#### R1-02 FastAPI health endpoint (`S`)

- `GET /health/live`를 만든다.
- `GET /health/ready`에서 DB 연결과 필수 경로 접근 가능 여부를 확인한다.
- readiness 실패는 원인별 상태를 반환하되 비밀 경로 전체를 노출하지 않는다.

**검증**

- 프로세스 생존과 운영 준비 상태를 구분한다.
- DB 또는 경로 문제가 있을 때 readiness가 실패한다.

#### R1-03 worker 골격 (`S`)

- API와 같은 이미지에서 다른 command로 실행되는 worker 엔트리포인트를 만든다.
- 종료 신호를 받으면 현재 짧은 작업을 정리하고 종료한다.
- 아직 입력 처리를 하지 않고 설정·DB 준비 상태만 로그로 확인한다.

**검증**

- worker가 SIGTERM에 정해진 시간 안에 종료된다.
- 시작과 종료 로그에 service 필드가 있다.

#### R1-04 React/TypeScript 골격 (`S`)

- Vite React TypeScript 프로젝트를 만든다.
- React Router로 `/`와 404 경로를 만든다.
- 상대 경로를 사용하는 공용 fetch client를 만든다.
- loading/error/success 상태를 보여주는 최소 health 화면을 만든다.

**검증**

- TypeScript strict 검사가 통과한다.
- API 성공과 실패가 서로 다른 화면 상태로 보인다.
- 키보드 focus가 보인다.

#### R1-05 세 컨테이너 Compose 연결 (`M`)

- 백엔드 Dockerfile 하나로 `api`와 `worker`를 실행한다.
- multi-stage 프런트엔드 Dockerfile로 React를 빌드하고 Nginx에서 제공한다.
- Nginx가 `/api/*`와 `/health/*`를 `api` 컨테이너로 proxy한다.
- 호스트에는 `web` 포트만 기본 노출한다.
- 개발용 볼륨과 운영용 볼륨 경로를 `.env.example`에 연결한다.

**검증**

- `docker compose config`가 성공한다.
- 세 서비스가 모두 시작된다.
- 브라우저에서 `/`와 `/health/ready`에 접근할 수 있다.
- 존재하지 않는 `/api` 경로가 React HTML로 바뀌지 않는다.
- `docker compose down`으로 정상 종료된다.

#### R1-06 공통 검증 명령 연결 (`S`)

- format, lint, typecheck, backend unit, frontend unit 진입점을 연결한다.
- 아직 테스트가 적더라도 명령은 실패를 숨기지 않아야 한다.

### R1 종료 게이트 — M0

- [x] `web`, `api`, `worker`가 Compose로 시작하고 종료된다.
- [x] 브라우저에서 `/health/ready`의 readiness 상태를 확인할 수 있다.
- [x] 잘못된 환경 설정은 시작 시 실패한다.
- [x] Python과 TypeScript의 format/lint/typecheck가 통과한다.
- [x] `.env`와 비밀값이 Git 추적 대상이 아니다.

### 데모

브라우저에서 첫 화면을 열어 API 준비 상태를 확인하고, DB 경로를 의도적으로 잘못 설정했을 때 readiness 실패가 화면에 표시되는 것을 보여준다.

## 6. R2 — SQLite, 작업 큐, 입력 감지

### 목표

Syncthing 입력 폴더의 완성된 m4a를 안전하게 한 번만 등록하고, 처리할 작업을 SQLite에 남긴다.

### 선행조건

- M0 통과

### 작업 목록

#### R2-01 SQLite schema와 migration (`M`)

- 우선 필요한 `recordings`, `jobs`, `artifacts`, `audit_events` 테이블부터 만든다.
- migration 버전을 DB에 기록한다.
- DB 연결 시 foreign key와 필요한 SQLite pragma를 명시한다.
- 아직 사용하지 않는 화자 세부 테이블은 R5에서 추가한다.

**검증**

- 빈 DB가 최신 schema로 생성된다.
- 같은 migration을 다시 실행해도 안전하다.
- 알려지지 않은 미래 schema는 조용히 덮어쓰지 않는다.

#### R2-02 recording/job 저장 연산 (`S`)

- 녹음 등록과 최초 job 생성을 하나의 트랜잭션으로 묶는다.
- 같은 콘텐츠 해시의 녹음이 하나만 존재하도록 DB 제약을 둔다.
- 같은 녹음/종류의 활성 job이 중복되지 않게 한다.

**검증**

- 같은 해시를 동시에 두 번 등록해도 recording과 job이 하나다.
- recording 저장만 되고 job 저장이 실패하는 중간 상태가 남지 않는다.

#### R2-03 안정 파일 판정 (`S`)

- `.m4a`만 대소문자 구분 없이 찾는다.
- 크기와 수정 시간이 `FILE_STABLE_SECONDS` 동안 변하지 않은 파일만 후보로 만든다.
- 심볼릭 링크와 알려진 임시 파일 패턴을 제외한다.

**검증**

- 복사 중 크기가 변하는 파일은 등록되지 않는다.
- 안정된 파일은 다음 scan에서 등록 후보가 된다.
- 심볼릭 링크가 입력 루트 밖 파일을 처리하게 만들지 못한다.

#### R2-04 ffprobe 입력 검사 (`S`)

- shell 없이 인자 배열로 ffprobe를 실행한다.
- 오디오 stream, 길이, 기본 메타데이터를 읽는다.
- 손상, timeout, 실행 파일 없음 오류를 구분한다.

**검증**

- 유효 fixture와 손상 fixture를 구분한다.
- 공백·한글·특수문자가 있는 파일명을 안전하게 처리한다.

#### R2-05 스트리밍 SHA-256 중복 방지 (`S`)

- 파일 전체를 메모리에 올리지 않고 콘텐츠 해시를 계산한다.
- 같은 바이트의 다른 파일명은 기존 recording과 연결하고 새 STT job을 만들지 않는다.
- 같은 경로의 내용이 달라지면 새 recording으로 처리한다.

**검증**

- 중복 인수 시나리오 1~3을 자동 테스트로 고정한다.

#### R2-06 단일 worker job claim (`M`)

- `queued` job 하나를 원자적으로 `running`으로 점유한다.
- attempt, locked_at, available_at을 기록한다.
- SIGTERM 또는 예외 시 작업 상태가 추적 가능하게 남는다.
- 실제 처리 대신 아직은 성공/실패를 선택할 수 있는 작은 handler를 사용한다.

**검증**

- worker를 두 번 잘못 실행해도 같은 job을 동시에 처리하지 않는다.
- 실패 원인과 시도 횟수가 보존된다.

#### R2-07 입력 감지 통합 테스트 (`M`)

- 임시 입력 폴더, 임시 DB, fixture로 scanner와 worker를 함께 실행한다.
- 재시작, 중복 파일명, 손상 파일을 포함한다.

### R2 종료 게이트 — M0.5

**검증**

- 같은 job을 재실행해도 성공 artifact가 중복되지 않는다.

#### R3-04 원자적 artifact writer (`M`)

- transcript/summary JSON과 Markdown을 임시 파일에 쓴 뒤 rename한다.

- DB 등록 실패와 파일 쓰기 실패를 각각 주입해 복구 동작을 검증한다.

**검증**

- 중간 파일이 최종 결과로 보이지 않는다.

**검증**

## 8. R4 — 실제 WhisperX STT와 pyannote 화자 분리

### 목표

가짜 speech 어댑터를 실제 미디어 표준화, WhisperX `large-v3`, alignment, pyannote diarization 구현으로 교체한다.

### 선행조건

- M1 통과
- Linux GPU 장비 사용 가능
- pyannote 모델 접근 가능

### 작업 목록

#### R4-01 GPU worker runtime과 모델 의존성 (`M`)

- 호환되는 CUDA, PyTorch, WhisperX, pyannote 조합을 lockfile과 이미지에 고정한다.
- 실제 모델용 worker만 GPU 접근을 요구하도록 Compose profile 또는 override를 둔다.
- fake worker는 GPU가 없는 개발 장비에서도 계속 실행되게 한다.
- 모델 cache를 영속 볼륨에 두고 애플리케이션 결과물과 분리한다.
- 컨테이너에서 GPU 접근을 확인하는 명시적 smoke 명령을 둔다.

**검증**

- Linux GPU 환경에서 컨테이너가 CUDA 장치를 확인한다.
- GPU가 없는 환경에서도 fake Compose smoke가 계속 통과한다.
- 의존성 버전이 개발자별로 임의 변경되지 않는다.

#### R4-02 FFmpeg 표준화 (`S`)

- 원본을 변경하지 않고 작업 임시 디렉터리에 mono PCM 16 kHz WAV를 만든다.
- timeout, disk full, 잘못된 stream 오류를 구조화한다.
- 성공/실패 후 임시 파일 정리 규칙을 구현한다.

#### R4-03 WhisperX 전사 어댑터 (`M`)

- `large-v3`, device, compute type, batch size를 검증된 설정으로 전달한다.
- 언어 자동 감지 또는 `WHISPER_LANGUAGE` 고정을 지원한다.
- 모델/라이브러리/설정 fingerprint를 결과에 저장한다.
- OOM과 모델 로드 실패를 구분한다.

#### R4-04 alignment (`S`)

- 감지 언어에 맞는 alignment를 수행한다.
- 단어 시간이 없는 구간도 전체 작업을 깨뜨리지 않고 segment 수준에서 표시한다.
- 시간 값이 오디오 범위를 벗어나지 않게 정규화·검증한다.

#### R4-05 pyannote diarization (`M`)

- pyannote 화자 구간을 생성한다.
- 텍스트 segment에 `SPEAKER_00` 형식의 임시 화자를 할당한다.
- 겹침 발화와 미배정 구간을 명시적으로 표현한다.

#### R4-06 실제 결과 정규화와 저장 (`M`)

- 실제 모델 응답을 R3의 내부 schema로 변환한다.
- segment 시간순, 양수 길이, 오디오 범위, 화자 ID 형식을 검증한다.
- 원시 응답이 아니라 정규화 결과만 이후 단계가 사용하게 한다.

#### R4-07 모델 오류와 재시도 분류 (`S`)

- OOM, 토큰 권한, 모델 다운로드, 손상 입력, 일시적 I/O 오류를 구분한다.
- 설정 조치가 필요한 오류는 무의미하게 자동 재시도하지 않는다.

#### R4-08 고정 음성 평가 (`M`)

- 단일 화자, 여러 화자, 무음 포함 표본을 처리한다.
- 전체 문장 완전 일치보다 시간 불변식과 화자 구간 생성 여부를 우선 검증한다.
- 실행 장비, model fingerprint, batch size, 처리 시간을 결과에 기록한다.

### R4 종료 게이트 — M2

- [x] 실제 모델 평가는 일반 CI와 분리되어 재현 가능하다.

## 9. R5 — 수동 화자 검토 GUI

### 목표

사용자가 임시 화자의 음성을 듣고 실제 인물을 정의하며, 잘못 배정된 발화를 직접 수정할 수 있게 한다. 이 단계가 끝나면 화자 데이터 축적이 시작된다.

### 선행조건

- M2 통과
- segment와 임시 화자 schema 안정화

### 작업 목록

#### R5-01 화자 DB schema (`M`)

- `recording_speakers`, `persons`, `speaker_embeddings` 테이블을 추가한다.
- segment에 person, speaker source, score, revision을 연결한다.
- 표시 이름은 중복 가능하고 ID로 구분한다.

#### R5-02 대표 클립 선택과 생성 (`M`)

- 너무 짧거나 겹침이 큰 구간을 제외한다.
- 각 임시 화자에서 서로 떨어진 대표 구간 2~3개를 선택한다.
- FFmpeg로 짧은 클립을 원자적으로 생성하고 artifact로 등록한다.
- 적합한 구간이 부족하면 자동 확정 불가 상태로 표시한다.

#### R5-03 media range API (`M`)

- artifact ID로 원본/대표 클립을 stream한다.
- 유효한 Range 요청에 206과 올바른 헤더를 반환한다.
- 허용된 미디어 루트 밖 경로를 거부한다.
- 파일명이나 절대 경로를 브라우저에 노출하지 않는다.

#### R5-04 인물과 화자 수정 API (`M`)

- 인물 목록/생성/이름 수정 API를 만든다.
- 임시 화자 전체를 인물에 연결하는 API를 만든다.
- 개별/일괄 segment 화자 변경 API를 만든다.
- 모든 쓰기에 기대 revision을 요구한다.
- `manual` 선택이 `auto`보다 우선하도록 한다.

#### R5-05 화자 검토 React 화면 (`M`)

- 임시 화자 카드, 대표 클립, 발화량, 후보 영역을 배치한다.
- 기존 인물, 새 인물, 알 수 없음을 선택할 수 있게 한다.
- 선택한 임시 화자의 transcript 발화를 강조한다.
- timestamp 클릭 시 전체 오디오를 해당 시점으로 이동한다.

#### R5-06 발화 개별/일괄 수정 (`M`)

- 발화 행 선택과 일괄 화자 변경을 구현한다.
- 저장 전 변경 요약을 표시한다.
- 저장되지 않은 변경이 있으면 화면 이탈을 경고한다.
- 저장 중 중복 제출을 막는다.

#### R5-07 revision 충돌 UX (`S`)

- 409를 일반 오류와 구분한다.
- 최신 revision을 다시 불러오도록 안내한다.
- 사용자 확인 없이 로컬 변경이나 서버 최신 값을 덮어쓰지 않는다.

#### R5-08 수정 후 무효화와 렌더 (`M`)

- 화자 이름/배정 변경 시 transcript를 다시 렌더한다.
- 기존 summary가 있다면 stale 처리하고 재생성 작업을 등록한다.
- STT와 diarization은 불필요하게 다시 실행하지 않는다.

#### R5-09 접근성·브라우저 E2E (`M`)

- label, 접근 가능한 버튼 이름, focus, 비색상 상태 표현을 확인한다.
- 키보드로 클립 재생, 인물 선택, 저장을 수행한다.
- 대표 클립 청취→새 인물 생성→일괄 수정→저장 흐름을 E2E로 고정한다.

### R5 종료 게이트 — M3

- [ ] 사용자가 대표 클립을 듣고 새 인물을 만들 수 있다.
- [ ] 임시 화자 전체와 개별 발화를 수정할 수 있다.
- [ ] 일괄 수정과 저장 전 변경 확인이 동작한다.
- [ ] 409 충돌이 자동 덮어쓰기 없이 처리된다.
- [ ] 수정 이후 DB, JSON, Markdown, UI가 일치한다.
- [ ] 키보드만으로 핵심 검토 흐름을 완료할 수 있다.

### 데모

`SPEAKER_00`의 대표 클립을 듣고 새 인물을 만든 뒤, 잘못 배정된 발화 하나를 `SPEAKER_01`의 인물로 바꾸고 transcript가 재생성되는 것을 보여준다.

## 10. R6 — 보수적인 화자 자동 식별

### 목표

수동으로 축적된 화자 자료를 사용해 고신뢰 경우만 자동 연결한다. 편의 기능이며 신원 인증이 아님을 UI에 명확히 표시한다.

### 선행조건

- M3 통과
- 같은 사람과 다른 사람의 수동 확정 표본 확보

### 작업 목록

#### R6-01 embedding 생성·버전 관리 (`M`)

- 수동 확정된 깨끗한 대표 구간에서 embedding을 생성한다.
- 모델과 전처리 버전을 함께 저장한다.
- 호환되지 않는 버전끼리 비교하지 않는다.

#### R6-02 인물 프로필 계산 (`M`)

- 인물별 여러 embedding을 프로필로 집계한다.
- 사용자가 연결을 취소한 구간은 제외한다.
- 표본이 부족한 인물은 자동 확정 후보로 사용하지 않는다.

#### R6-03 후보 점수와 자동 확정 규칙 (`M`)

- best score와 second-best score를 계산한다.
- 절대 threshold와 1·2위 margin을 모두 적용한다.
- 같은 녹음의 서로 다른 임시 화자를 같은 인물로 자동 연결하지 않는다.
- 자동 결정 전 기능 flag를 확인한다.

#### R6-04 후보 근거 UI (`S`)

- 후보 이름, 유사도, 1·2위 차이, 자동/수동 출처를 표시한다.
- 낮은 신뢰도와 표본 부족 이유를 설명한다.
- 사용자가 자동 연결을 취소하거나 다른 인물로 바꿀 수 있게 한다.

#### R6-05 threshold 보정 평가 (`M`)

- 같은 사람, 다른 사람, 애매한 표본으로 점수 분포를 만든다.
- 잘못된 자동 연결을 줄이는 방향으로 threshold와 margin을 선택한다.
- 표본, 모델 fingerprint, 선택 근거를 기록한다.
- 근거가 충분하지 않으면 자동 확정을 계속 끄고 후보 추천만 제공한다.

#### R6-06 회귀 평가 (`S`)

- 알려진 동일 화자, 다른 화자, 애매한 화자 결과를 고정 평가로 남긴다.
- 모델/전처리/threshold 변경 시에만 실제 평가를 다시 실행한다.

### R6 종료 게이트 — M4

- [ ] 수동 확정 자료만 프로필에 사용된다.
- [ ] 고신뢰와 충분한 margin을 함께 만족해야 자동 연결된다.
- [ ] 애매한 표본은 수동 검토로 남는다.
- [ ] 사용자가 자동 연결을 취소할 수 있다.
- [ ] 평가 근거 없이 자동 확정 기능을 활성화하지 않는다.

### 데모

알려진 화자는 자동 연결되고, 점수가 비슷한 두 후보가 있는 화자는 검토 대기로 남으며, UI에서 각 결정 근거를 확인하는 흐름을 보여준다.

## 11. R7 — 전체 내용 분류와 transcript 문서

### 목표

화자 검토가 끝난 전체 transcript를 허용된 대분류 중 하나로 분류하고, 사람이 읽을 수 있는 versioned JSON/Markdown 문서를 생성한다.

### 선행조건

- M3 통과
- R6는 병행 가능하며 필수 선행조건은 아님
- LLM 개인정보 경로 결정

### 작업 목록

#### R7-01 범주 설정 검증 (`S`)

- `CATEGORIES`와 `AUTO_SUMMARY_CATEGORIES`를 시작 시 검증한다.
- 자동 요약 범주가 허용 범주 밖이면 시작을 실패시킨다.
- 표시 이름과 안전한 category slug를 구분한다.

#### R7-02 구조화 분류 어댑터 (`M`)

- 전체 transcript와 허용 범주만 분류 입력으로 제공한다.
- category, confidence, reason schema를 검증한다.
- 허용되지 않은 범주나 깨진 JSON은 한 번 교정 후 실패 처리한다.
- 모델, 프롬프트, temperature, schema 버전을 기록한다.

#### R7-03 긴 transcript 처리 (`M`)

- context 한도 안이면 전체 문서를 한 번에 분류한다.
- 한도를 넘을 때만 부분 주제 추출 후 전체 분류를 수행한다.
- 단순 앞부분 샘플링으로 전체 범주를 결정하지 않는다.

#### R7-04 transcript JSON/Markdown renderer (`M`)

- JSON에 segment의 정밀 시간과 화자 ID를 보존한다.
- Markdown에는 녹음 메타데이터, 범주, timestamp, 표시 이름을 렌더한다.
- 인접 발화를 읽기 좋게 합치되 JSON 원본은 변경하지 않는다.
- 임시 파일과 원자적 rename 규칙을 사용한다.

#### R7-05 범주 수정 API/GUI (`M`)

- 녹음 상세에서 자동 분류, confidence, reason을 표시한다.
- 허용 목록 안에서 사용자가 범주를 수정할 수 있게 한다.
- 수동 분류가 자동 결과보다 우선한다.
- revision 충돌과 summary 무효화를 처리한다.

#### R7-06 분류 평가와 실패 테스트 (`M`)

- 강의, 일상 대화, 회의, 게임 목록, 기타의 대표 fixture를 준비한다.
- 허용 범주, schema, 필수 이유 필드를 검증한다.
- timeout, 깨진 응답, 알 수 없는 범주가 안전하게 실패하는지 확인한다.

### R7 종료 게이트 — M5

- [ ] 모든 성공 결과가 허용된 범주 중 하나다.
- [ ] 전체 내용 또는 긴 문서 축약 결과를 사용해 분류한다.
- [ ] 사용자가 범주를 수정할 수 있다.
- [ ] transcript JSON과 Markdown이 같은 revision을 표현한다.
- [ ] 범주 수정 후 artifact와 UI가 일치한다.

### 데모

회의 녹음을 분류해 transcript Markdown을 생성하고, 사용자가 범주를 변경했을 때 문서 메타데이터가 갱신되는 것을 보여준다.

## 12. R8 — 자동·수동 요약

### 목표

범주 정책 또는 사용자 요청에 따라 근거 중심 요약을 생성하고 `${SUMMARY_ROOT}/<category_slug>/요약/`에 저장한다.

### 선행조건

- M5 통과
- 사용할 LLM과 개인정보 전송 정책 확정

### 작업 목록

#### R8-01 범주별 summary schema (`M`)

- 강의, 회의, 일상 대화, 게임 목록, 기타의 최소 출력 구조를 정의한다.
- 할 일의 담당자·기한·내용을 nullable 필드로 구분한다.
- 근거가 없을 때 “확인되지 않음”을 표현할 수 있게 한다.

#### R8-02 요약 어댑터와 출력 검증 (`M`)

- transcript에 없는 사실을 만들지 않도록 프롬프트 규칙을 적용한다.
- JSON을 먼저 schema로 검증한 뒤 Markdown으로 렌더한다.
- 모델, 프롬프트, template, transcript revision을 기록한다.
- 깨진 응답을 조용히 정상 요약으로 저장하지 않는다.

#### R8-03 자동/수동 작업 등록 (`M`)

- 분류 직후 자동 요약 범주면 job을 하나 등록한다.
- 비대상 범주는 사용자 요청 전 job을 만들지 않는다.
- 같은 recording revision의 활성/성공 job을 중복 생성하지 않는다.

#### R8-04 안전한 경로와 artifact (`S`)

- category slug에서 `/`, `..`, 제어 문자를 거부한다.
- 요약 JSON/Markdown을 원자적으로 저장한다.
- 범주 변경 시 새 경로 생성 성공 후 이전 artifact를 정리한다.

#### R8-05 요약 React UI (`M`)

- 상세 화면에서 요약 없음, 생성 중, 완료, stale, 실패를 구분한다.
- 수동 요약 요청과 중복 클릭 방지를 구현한다.
- 요약 실패 시 원인과 재시도 동작을 제공한다.

#### R8-06 수정에 따른 stale 처리 (`M`)

- 화자 이름/배정, transcript 텍스트, 범주 변경에 맞춰 요약을 무효화한다.
- 최신 revision 요약이 생성되기 전까지 이전 요약을 최신처럼 표시하지 않는다.

#### R8-07 요약 평가 (`M`)

- 결정 사항, 담당자, 기한의 근거 유무를 fixture로 검증한다.
- 문장 완전 일치 대신 schema, 필수 사실 보존, 금지된 환각을 검사한다.
- 자동 범주와 수동 범주 흐름을 각각 E2E로 확인한다.

### R8 종료 게이트 — M6

- [ ] 자동 요약 범주는 분류 후 한 번 요약된다.
- [ ] 비대상 범주는 사용자가 요청할 때만 요약된다.
- [ ] 요약이 범주별 `요약/` 경로 규칙을 따른다.
- [ ] 근거 없는 담당자·날짜·결정이 정상 필드로 확정되지 않는다.
- [ ] 입력 revision이 바뀌면 이전 요약이 stale로 표시된다.
- [ ] 브라우저에서 요청, 진행, 완료, 실패를 구분할 수 있다.

### 데모

회의는 자동으로 요약되고 일상 대화는 버튼을 누른 뒤 요약되며, 화자 이름을 수정했을 때 기존 요약이 stale 후 재생성되는 것을 보여준다.

## 13. R9 — 운영 안정화와 릴리스 후보

### 목표

정상 기능 구현 이후 재시작, 실패, 로그, 백업, 접근성, 보안을 검증해 실제 운영 후보를 만든다.

### 작업 목록

#### R9-01 stale job 회수 (`M`)

#### R9-02 오류 분류와 재시도 UI (`M`)

- 일시 오류와 사용자/설정 조치 오류를 구분한다.
- 지수 backoff와 최대 자동 시도 횟수를 적용한다.
- 실패 상세에 오류 코드, 설명, 단계, 시도 횟수, 재시도 버튼을 표시한다.

#### R9-03 구조화 로그와 대시보드 운영 정보 (`S`)

- recording ID, job ID, stage, attempt, duration, error code를 로그에 넣는다.
- 대시보드에서 대기/진행/검토/실패 수와 최근 처리 시각을 보여준다.
- transcript, prompt, 비밀값을 로그에 남기지 않는다.

#### R9-04 백업·복원 절차 (`M`)

- SQLite online backup 또는 안전한 정지 백업 절차를 만든다.
- DB, 원본, transcript JSON, 화자 프로필을 백업 대상으로 정의한다.
- 빈 임시 환경에서 복원 smoke를 한 번 수행한다.
- 자동 삭제나 자동 보관 만료는 아직 구현하지 않는다.

#### R9-05 컨테이너 권한과 경로 보안 (`M`)

- 가능한 비-root 사용자로 실행한다.
- API, worker, web의 볼륨 권한을 최소화한다.
- 입력/출력 루트 밖 접근, 심볼릭 링크, path traversal을 검증한다.
- 호스트 기본 bind 주소 `0.0.0.0:38000`이 신뢰할 수 있는 LAN과 방화벽 안에서만 노출되는지 확인한다.

#### R9-06 UX 상태와 접근성 마감 (`M`)

- 대시보드 filter와 실패 화면을 완성한다.
- 모든 주요 화면의 loading, empty, error, success를 확인한다.
- label, focus, 키보드 탐색, 비색상 상태 표현, 휴대폰 기본 레이아웃을 점검한다.

#### R9-07 전체 E2E와 Compose smoke (`M`)

- 대시보드→화자 검토→수정→분류→요약→실패 재시도의 핵심 흐름을 실행한다.
- worker 강제 종료, API 재시작, Compose 재시작을 포함한다.
- 테스트 후 생성 데이터를 격리된 환경에서 정리한다.

#### R9-08 운영 문서 초안 (`S`)

- 설치, `.env`, Compose 실행/종료, 로그 확인, 실패 재시도, 백업/복원을 README에 기록한다.
- Linux GPU와 macOS 개발 환경 차이를 명시한다.
- 외부 LLM 사용 시 데이터 전송 사실을 명시한다.

### R9 종료 게이트 — M7

- [ ] worker 강제 종료 후 stale job이 안전하게 회수된다.
- [ ] 실패 원인과 재시도 가능 여부를 GUI에서 구분한다.

## 14. R10 — 실제 환경 인수와 첫 릴리스

### 목표

실제 Syncthing 입력, 실제 GPU 모델, 실사용 녹음 표본으로 설계도의 20개 인수 시나리오를 검증하고 운영 가능한 첫 버전을 확정한다.

### 선행조건

- M7 통과
- 실제 Linux GPU 운영 장비
- 실제 Syncthing 입력 폴더
- 사용 허가된 실사용 음성 표본

### 작업 목록

#### R10-01 운영 환경 배치 (`M`)

- 실제 디렉터리를 `.env`에 연결한다.

- web만 의도한 주소와 포트로 노출한다.

#### R10-03 20개 인수 시나리오 실행 (`M`)

- 설계도 17절의 A~E 시나리오를 하나씩 실행한다.
- 각 시나리오에 기대 DB 상태, 파일, 로그, GUI 결과를 기록한다.
- 실패한 시나리오는 버그 작업으로 분리하고 전체 재실행 전에 관련 회귀 테스트를 추가한다.

#### R10-04 장비와 화자 threshold 보정 (`M`)

- 실제 GPU에 맞는 batch size와 compute type을 결정한다.
- 같은 사람/다른 사람 표본으로 자동 식별 threshold와 margin을 보정한다.
- 근거가 부족하면 자동 확정을 끄고 후보 추천만 릴리스한다.

#### R10-05 재부팅·복원 훈련 (`M`)

- 처리 중 호스트 또는 Compose 재시작을 시험한다.
- 중복 STT, 유실 artifact, 영구 `running` job이 없는지 확인한다.
- 최신 백업에서 별도 디렉터리로 복원한다.

#### R10-06 사용자 수행 시험 (`M`)

- 사용자가 개발자 도움 없이 다음 흐름을 수행한다.
  1. 새 녹음 확인
  2. 미확정 화자 클립 청취
  3. 새/기존 인물 연결
  4. 잘못된 발화 수정
  5. 범주 확인 또는 수정
  6. 자동/수동 요약 확인
  7. 실패 작업 확인과 재시도
- 막힌 지점은 우선 문서 문제가 아닌 UX 문제인지 판정한다.

#### R10-07 릴리스 기준 확정 (`S`)

- Compose 이미지와 dependency lockfile을 고정한다.
- migration과 artifact schema 버전을 확인한다.
- 알려진 제한과 보류 기능을 release note에 기록한다.
- 인수 증거와 최종 운영 설정 항목을 보존한다.

## 15. 단계 간 병행 가능 범위

핵심 경로는 순차적으로 진행하되, 계약이 정해진 뒤에는 일부 작업을 병행할 수 있다.

| 기준 작업 | 병행 가능한 작업 | 주의점 |
|---|---|---|
| R2 DB/job 구현 | R1 React 공통 컴포넌트 보강 | 녹음 API가 아직 없으므로 mock 화면을 제품 코드에 남기지 않는다. |
| R3 내부 transcript schema 확정 | R4 모델 어댑터, R5 화자 화면 fixture | schema 변경은 세 작업에 즉시 공유한다. |
| R4 실제 STT | R5 GUI를 fake transcript로 구현 | 실제 결과의 긴 텍스트와 미배정 화자 사례를 나중에 반드시 재검증한다. |
| R5 수동 화자 검토 | R7 분류 어댑터 | 분류는 화자 확정 완료 상태만 입력으로 받는다. |

병행 개발 시에도 DB migration, OpenAPI schema, artifact schema를 동시에 서로 다르게 수정하지 않는다. 공용 계약 변경은 한 작업에서 먼저 병합한 뒤 나머지가 따라간다.

## 16. 작업 보드 운영 규칙

### 16.1 상태

| 상태 | 의미 |
|---|---|
| `BACKLOG` | 로드맵에는 있으나 선행조건 미충족 |
| `READY` | 선행조건·인수 기준·검증 방법이 명확함 |
| `IN PROGRESS` | 현재 구현 중 |
| `VERIFY` | 코드 완료, 자동/수동 검증 중 |
| `DONE` | 단계 Definition of Done 충족 |
| `BLOCKED` | 외부 장비·토큰·결정이 없어 진행 불가 |

한 개발자는 원칙적으로 `IN PROGRESS` 작업 하나만 맡는다. 여러 작업을 동시에 열기보다 현재 작업을 검증까지 끝내는 것이 전체 흐름을 빠르게 만든다.

각 작업은 전용 브랜치에서 진행하고 Definition of Done 검증과 `docs/progress/NNN_<name>.md`
기록을 마친 뒤 해당 작업 단위로 커밋한다. 다음 작업은 이전 작업의 커밋이 완료된 뒤 새 브랜치에서
시작한다.

### 16.2 Definition of Ready

작업을 시작하기 전에 다음이 명확해야 한다.

- 연결되는 로드맵 작업 ID와 설계도 절
- 사용자 또는 시스템 관점의 목적
- 선행 작업 완료 여부
- 변경할 것으로 예상되는 계층
- 정상 경로 인수 기준
- 대표 실패 경로
- 실행할 자동 검증
- 이번 작업에서 하지 않을 것

### 16.3 작업별 Definition of Done

- 인수 기준이 모두 충족되었다.
- 정상 경로와 대표 실패 경로 테스트가 있다.
- format, lint, typecheck, 관련 테스트가 통과한다.
- API 변경은 OpenAPI와 프런트엔드 타입에 반영되었다.
- 상태/DB 변경은 재시작과 중복 실행 결과가 정의되어 있다.
- 파일 변경은 원자성, 경로 안전성, 실패 복구를 확인했다.
- UI 변경은 loading, empty, error, success와 키보드 조작을 확인했다.
- 로그에 비밀값과 전체 transcript가 포함되지 않는다.
- 필요한 `.env.example`, README, 설계 문서가 실제 동작과 일치한다.
- 생략한 검증이 있다면 이유와 실행 환경을 기록했다.

### 16.4 작업 티켓 템플릿

```markdown
## [R3-04] 원자적 artifact writer

### 목적
완성되지 않은 transcript/summary가 최종 결과로 보이지 않게 한다.

### 선행조건
- R3-01 내부 schema 완료
- R2-01 artifacts table 완료

### 범위
- 같은 디렉터리 임시 파일 쓰기
- flush/close 후 atomic rename
- artifact hash와 schema version DB 등록

### 비범위
- 원격 객체 저장소
- 여러 노드 간 분산 lock

### 인수 기준
- 파일 쓰기 중 실패하면 최종 파일이 생기지 않는다.
- 재시도 후 artifact가 하나만 등록된다.

### 검증
- backend unit: writer failure injection
- integration: DB 등록 실패 후 재실행
- 전체 test
```

## 19. 주요 위험과 중단 기준

### GPU 또는 모델 접근 지연

- **영향**: R4 실제 모델 검증이 막힌다.
- **계속 가능한 작업**: R1~R3, fake transcript 기반 R5 UI 골격, R7/R8 schema 작업.
- **중단 기준**: 실제 결과 정규화와 성능 값을 추측해서 완료 처리하지 않는다.

### 화자 자동 식별 오탐

- **영향**: 잘못된 인물이 transcript와 요약에 확정된다.
- **대응**: 절대 threshold와 margin을 함께 적용하고 수동 취소를 제공한다.
- **중단 기준**: 같은 사람/다른 사람 평가 자료가 부족하면 자동 확정을 활성화하지 않는다. 후보 추천만 제공한다.

### 외부 LLM 개인정보 전송 미결정

- **영향**: R7/R8 실제 공급자 호출을 확정할 수 없다.
- **계속 가능한 작업**: fake 어댑터, schema, renderer, UI, 실패 흐름.
- **중단 기준**: 사용자가 인지하지 않은 상태로 실제 transcript를 외부 서비스에 보내지 않는다.

### SQLite와 공유 파일 시스템

- **영향**: 네트워크 파일 시스템에 DB를 두면 lock/내구성 문제가 생길 수 있다.
- **대응**: `APP_DATA_DIR`의 SQLite는 컨테이너 호스트 로컬 디스크에 둔다.
- **확장 조건**: 다중 worker 또는 다중 호스트가 실제 요구되면 PostgreSQL과 외부 큐를 별도 설계한다.

### 긴 녹음의 자원 고갈

- **영향**: GPU OOM, 긴 처리 시간, 큰 브라우저 transcript가 발생한다.
- **대응**: batch size 조절, segment 페이지네이션, 명시적 오류를 먼저 사용한다.
- **확장 조건**: 실제 표본에서 반복 실패할 때만 오디오 chunk 처리와 checkpoint를 추가한다.

### Syncthing과 파일 안정화 오판

- **영향**: 미완성 녹음을 읽거나 같은 파일을 다시 처리할 수 있다.
- **대응**: 크기/mtime 안정화, ffprobe, 콘텐츠 해시를 모두 통과해야 등록한다.
- **중단 기준**: 파일명 또는 존재 여부만으로 완료를 판단하지 않는다.

단계가 끝날 때만 아래 표의 상태와 증거 링크를 갱신한다.

이 묶음의 최종 결과는 기능이 많은 애플리케이션이 아니라, 다음 개발을 안전하게 반복할 수 있는 실행 가능한 빈 골격이다.

```text
docker compose up -d
  -> web 접속 성공
  -> /health/live 성공
  -> /health/ready 성공
  -> api/worker 로그 구분 가능
  -> format/lint/typecheck/test 성공
  -> docker compose down 성공
```

M0를 통과하기 전에는 DB 작업 큐나 실제 AI 모델을 동시에 붙이지 않는다. 실행·설정·검증의 기준선이 먼저 안정되어야 이후 오류를 빠르게 분리할 수 있다.
