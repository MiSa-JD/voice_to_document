# 음성 기록 자동 문서화 시스템 구현 설계도

> 상태: 구현 기준 초안 1.0
> 기준 문서: `docs/00_first_destination.md`
> 이 문서는 기준 문서를 변경하지 않고, 그 요구사항을 구현 가능한 수준으로 구체화한다.

## 1. 문서의 목적

이 문서는 Syncthing으로 전달된 음성 파일을 감지한 뒤 STT, 화자 분리·식별, 문서 분류, 선택적 요약까지 수행하는 로컬 우선(local-first) 시스템의 구현 기준을 정의한다.

구현 중 선택지가 생기면 다음 우선순위를 따른다.

1. 원본 녹음과 이미 생성된 결과물을 잃지 않는다.
2. 같은 입력을 여러 번 감지하거나 프로세스가 재시작되어도 결과가 중복 생성되지 않는다.
3. 자동 판단은 신뢰도가 충분할 때만 적용하고, 나머지는 사용자가 수정할 수 있게 한다.
4. 처리 상태와 실패 원인을 사용자가 확인할 수 있게 한다.
5. 초기 버전은 한 대의 장비와 한 명의 사용자를 대상으로 단순하게 유지한다.

## 2. 목표와 완료 조건

### 2.1 목표

시스템은 다음 흐름을 끝까지 처리해야 한다.

```text
휴대폰 녹음
  -> Syncthing 입력 폴더
  -> 안정적으로 복사가 끝난 m4a 감지
  -> 중복 여부 확인
  -> WhisperX large-v3 STT
  -> pyannote 화자 분리
  -> 기존 화자 자동 식별 또는 사용자 확인 대기
  -> 전체 내용 기준 대분류
  -> 분류 정책 또는 사용자 요청에 따른 요약
  -> 파일 결과물 저장 및 UI에서 상태 확인/수정
```

### 2.2 시스템 수준 완료 조건

아래 조건이 모두 충족되면 첫 번째 목적지의 구현이 완료된 것으로 본다.

- 새 `.m4a` 파일이 입력 폴더에 들어오면 별도 명령 없이 처리된다.
- 같은 음성 파일을 이름만 바꾸어 다시 넣어도 STT가 중복 실행되지 않는다.
- STT 결과에 시간 구간과 화자 ID가 포함된다.
- 모르는 화자는 대표 음성 구간을 들으며 사용자가 이름을 지정할 수 있다.
- 충분히 유사한 기존 화자는 자동으로 연결되고, 애매한 경우 자동 확정되지 않는다.
- 사용자가 화자 이름과 잘못 배정된 발화 구간을 수정할 수 있다.
- 전체 대화 내용이 설정된 큰 범주 중 하나로 분류된다.
- 자동 요약 대상 범주는 자동으로, 그 외 범주는 사용자 요청 시 요약된다.
- 요약 결과는 `${SUMMARY_ROOT}/<범주>/요약/` 아래에 저장된다.
- 녹음, STT, 화자 자료, 요약 저장 위치를 `.env`에서 변경할 수 있다.
- `docker compose up -d`와 `docker compose down`으로 실행과 종료가 가능하다.
- 실패한 작업은 원인을 남기고 안전하게 재시도할 수 있다.

## 3. 범위

### 3.1 첫 버전에 포함하는 것

- `.m4a` 입력 감지와 파일 복사 완료 확인
- 콘텐츠 해시 기반 중복 방지
- WhisperX `large-v3` 기반 STT와 단어/문장 시간 정렬
- pyannote 기반 화자 분리
- 녹음별 임시 화자(`SPEAKER_00`)와 실제 인물의 연결
- 대표 음성 클립을 이용한 수동 화자 확인
- 누적된 화자 임베딩을 이용한 보수적 자동 식별
- 발화 구간의 화자 수정
- 설정 가능한 대분류 목록과 전체 문서 분류
- 범주별 자동 요약 정책과 수동 요약 요청
- Markdown/JSON 결과물
- 처리 현황, 실패, 화자 검토·수정, 분류, 요약을 다루는 React 웹 UI와 API
- Docker Compose 실행
- SQLite 기반 상태 관리

### 3.2 첫 버전에서 제외하는 것

- 여러 사용자와 권한 관리
- 모바일 앱 또는 녹음 기능 자체
- Syncthing 설치와 기기 간 페어링 자동화
- 여러 GPU에 분산하는 처리
- 실시간 스트리밍 STT
- 클라우드 저장소 동기화
- 화자의 성문 인증 또는 보안 신원 확인
- 사용자가 자유롭게 만드는 복잡한 워크플로 엔진
- 검색용 벡터 데이터베이스와 RAG
- 대규모 처리용 Redis, Celery, Kafka

화자 자동 식별은 편의를 위한 유사도 판정이지 신원 인증이 아니다. 잘못된 자동 식별을 완전히 방지할 수 없으므로 UI에서 근거 점수와 수정 기능을 제공한다.

## 4. 실행 환경과 기술 기준

### 4.1 권장 실행 환경

- 운영체제: NVIDIA Container Toolkit을 사용할 수 있는 Linux
- GPU: CUDA를 지원하며 `large-v3`를 실행할 수 있는 VRAM을 가진 NVIDIA GPU
- 저장소: 녹음 원본과 파생 파일을 담을 충분한 로컬 디스크
- 네트워크: 모델 최초 다운로드와 외부 LLM을 선택한 경우에만 필요

Docker Desktop for macOS는 일반적인 Linux CUDA 컨테이너 방식으로 호스트 GPU를 전달하지 못하므로, Apple Silicon Mac에서 Compose만으로 `large-v3` GPU 처리를 운영하는 것은 첫 버전의 기준 환경으로 삼지 않는다. 개발 시에는 STT 어댑터를 가짜 구현으로 바꾼 통합 테스트를 실행하고, 실제 모델 검증은 Linux GPU 장비에서 수행한다.

### 4.2 최소 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.11 | WhisperX/pyannote 생태계와 직접 연결된다. |
| 백엔드 API | FastAPI | 작업 상태와 사용자 수정 명령을 명확한 JSON 계약으로 제공한다. |
| 프런트엔드 런타임 | Node.js 24 LTS, npm | 현재 LTS 런타임을 Dockerfile과 lockfile로 고정한다. |
| 프런트엔드 | React + TypeScript + Vite + React Router | 화자 청취·분류·발화 수정을 독립된 GUI로 제공하고 타입으로 API 실수를 줄인다. |
| 웹 제공 | Nginx | 빌드된 프런트엔드를 제공하고 `/api`와 오디오 요청을 API로 프록시한다. |
| 프런트엔드 테스트 | Vitest + React Testing Library, Playwright | 컴포넌트 동작과 실제 브라우저의 핵심 흐름을 분리해 검증한다. |
| 상태 저장 | SQLite | 한 장비·단일 worker에 충분하고 백업이 단순하다. |
| 작업 실행 | DB 작업 큐를 읽는 단일 Python worker | 별도 브로커 없이 재시도와 상태 추적을 제공한다. |
| STT | WhisperX + `large-v3` | 기준 문서의 명시적 요구사항이다. |
| 화자 분리 | pyannote.audio | 기준 문서의 명시적 요구사항이다. |
| 미디어 처리 | FFmpeg/ffprobe | 입력 검사, 표준화, 대표 클립 생성을 담당한다. |
| 문서 형식 | Markdown + JSON | 사람이 읽는 결과와 기계가 재처리할 원본을 함께 보존한다. |
| 배포 | Docker Compose | 한 명령 실행·종료 요구사항을 충족한다. |

### 4.3 단순화 원칙

- `api`와 `worker`는 같은 Docker 이미지를 사용하고 실행 명령만 다르게 한다.
- 프런트엔드 runtime dependency는 React와 라우팅에 필요한 최소 패키지로 시작하고 `package-lock.json`을 커밋한다.
- worker는 한 번에 하나의 GPU 작업만 처리한다.
- SQLite에는 상태와 메타데이터를 저장하고, 큰 오디오와 문서는 파일 시스템에 저장한다.
- AI 모델 호출은 얇은 어댑터 경계 뒤에 두되, 첫 구현은 선택한 공급자 하나만 지원한다.
- 성능 문제가 측정되기 전에는 Redis, 분산 큐, 벡터 DB를 추가하지 않는다.

## 5. 전체 구조

```text
┌─────────────────────┐
│ Syncthing input dir │
└──────────┬──────────┘
           │ scan + stable-file check
           v
┌─────────────────────┐       ┌──────────────────────┐
│ Worker              │<----->│ SQLite               │<─────┐
│ - discovery         │       │ recordings/jobs/...  │      │
│ - STT/diarization   │       └──────────────────────┘      │
│ - speaker matching  │                                     │
│ - classify/summarize│       ┌──────────────────────┐      │
│ - artifact writer   │       │ FastAPI JSON API     │──────┘
└──────────┬──────────┘       │ - queue/status       │
           │                  │ - corrections        │
           │                  │ - audio streaming    │
           │                  └──────────▲───────────┘
           │                             │ /api (JSON + media)
           │                  ┌──────────┴───────────┐
           │                  │ React web frontend   │
           │                  │ - speaker review     │
           │                  │ - transcript edits   │
           │                  │ - summary/status     │
           │                  └──────────────────────┘
           v
┌────────────────────────────────────────────────────┐
│ Configured storage roots                           │
│ transcript / speaker artifacts / summary / archive │
└────────────────────────────────────────────────────┘
```

### 5.1 컨테이너

Compose에는 세 서비스를 둔다. 프런트엔드도 첫 버전의 필수 서비스다.

| 서비스 | 역할 | GPU |
|---|---|---|
| `web` | 빌드된 React 앱 제공, `/api` 요청 reverse proxy | 불필요 |
| `api` | REST API, 오디오 range streaming | 불필요 |
| `worker` | 파일 감지, STT, 화자 처리, 분류, 요약 | 필요 |

`api`와 `worker`는 같은 SQLite DB와 설정된 결과물 디렉터리를 공유한다. `web`은 DB나 호스트 파일을 직접 보지 않고 API만 호출한다. SQLite 쓰기 경합을 줄이기 위해 worker는 하나만 실행하고, API의 수정 요청은 짧은 트랜잭션으로 처리한다.

### 5.2 프로세스 책임 경계

- API는 긴 AI 작업을 직접 실행하지 않는다. 요청을 DB 작업으로 등록하고 즉시 응답한다.
- worker만 녹음 처리 파이프라인을 진행한다.
- API만 사용자 수정 요청을 검증해 저장한다.
- 결과 파일 생성은 worker가 담당한다. 사용자 수정 직후 필요한 재생성도 작업으로 등록한다.
- 프런트엔드는 서버 상태를 자체적으로 추측하지 않는다. API가 반환한 상태, revision, 허용 동작을 기준으로 화면과 버튼을 구성한다.
- 첫 버전의 실행 상태 갱신은 짧은 polling으로 처리한다. 실측 전에는 WebSocket을 도입하지 않는다.

## 6. 저장소와 디렉터리 설계

### 6.1 애플리케이션 소스 구조

구현 시 다음 정도의 구조로 시작한다.

```text
.
├── backend/
│   ├── app/
│   │   ├── api.py             # FastAPI 엔트리포인트와 JSON 라우트
│   │   ├── worker.py          # 스캔 루프와 작업 실행
│   │   ├── config.py          # .env 검증 및 경로 설정
│   │   ├── db.py              # SQLite 연결과 마이그레이션
│   │   ├── models.py          # 공용 데이터 구조/상태 enum
│   │   ├── pipeline.py        # 단계 전이와 재처리 규칙
│   │   ├── media.py           # ffprobe, 변환, 클립 생성
│   │   ├── speech.py          # WhisperX/pyannote 연동
│   │   ├── speakers.py        # 임베딩, 후보 산정, 확정 규칙
│   │   └── documents.py       # 분류, 요약, Markdown/JSON 생성
│   └── tests/
├── frontend/
│   ├── src/
│   │   ├── api/               # fetch client와 API 타입
│   │   ├── components/        # 오디오 플레이어, 상태 배지, 공통 폼
│   │   ├── pages/             # 대시보드, 상세, 화자 검토, 인물 관리
│   │   └── main.tsx
│   ├── tests/
│   └── package.json
├── e2e/                       # 핵심 사용자 흐름만 다루는 브라우저 테스트
├── docs/
├── Dockerfile
├── frontend.Dockerfile
├── compose.yaml
├── pyproject.toml
├── .env.example
└── README.md
```

초기 구현에서 파일이 지나치게 짧게 쪼개지면 합쳐도 된다. 이 구조는 책임 경계이지 반드시 지켜야 할 파일 수가 아니다. 프런트엔드는 별도 상태 관리 라이브러리 없이 React state와 `fetch`로 시작하며, 서버 데이터 캐시 문제가 실제로 커질 때만 전용 라이브러리를 검토한다.

### 6.2 런타임 디렉터리

모든 루트는 절대 경로로 해석하며 시작 시 쓰기 가능 여부를 검사한다.

```text
${RECORDING_INPUT_DIR}/
└── *.m4a

${TRANSCRIPT_ROOT}/
└── <recording_id>/
    ├── transcript.json        # 시간, 화자, 원문을 보존하는 기준 결과
    └── transcript.md          # 사람이 읽는 현재 버전

${SPEAKER_ROOT}/
├── recordings/<recording_id>/
│   ├── SPEAKER_00/
│   │   ├── representative-01.m4a
│   │   └── representative-02.m4a
│   └── SPEAKER_01/...
└── profiles/<person_id>/
    └── profile.json           # 표시 이름과 임베딩 자료의 메타데이터

${SUMMARY_ROOT}/
└── <category_slug>/
    └── 요약/
        ├── <recording_id>.md
        └── <recording_id>.json

${APP_DATA_DIR}/
├── app.db
├── archive/                   # 선택: 처리 후 원본을 옮길 때만 사용
└── quarantine/                # 읽을 수 없는 입력 또는 수동 격리
```

`recording_id`는 파일명과 분리된 내부 식별자(UUID)를 사용한다. 사용자가 파일명을 바꾸어도 같은 콘텐츠는 SHA-256 해시로 기존 녹음과 연결한다.

### 6.3 파일 쓰기 규칙

- 모든 결과물은 같은 디렉터리에 임시 파일로 완전히 쓴 뒤 원자적 rename으로 교체한다.
- `transcript.json`이 구조화 데이터의 기준이고 Markdown은 언제든 다시 만들 수 있는 표현물이다.
- 원본 녹음은 기본적으로 삭제하거나 변경하지 않는다.
- 범주가 바뀌면 기존 요약 파일을 새 경로에 원자적으로 생성한 다음 이전 파일을 제거한다. 실패하면 기존 파일을 유지한다.
- 사람이 결과 파일을 직접 편집하는 운영은 지원하지 않는다. 수정은 UI/API를 통해 DB에 반영하고 파일을 재생성한다.

## 7. 환경 변수

`.env.example`은 아래 변수를 설명과 함께 제공한다. 비밀값이 들어 있는 실제 `.env`는 버전 관리하지 않는다.

| 변수 | 필수 | 예시/기본값 | 의미 |
|---|---:|---|---|
| `RECORDING_INPUT_DIR` | 예 | `/data/inbox` | Syncthing이 녹음을 넣는 폴더 |
| `TRANSCRIPT_ROOT` | 예 | `/data/transcripts` | STT 결과 저장 루트 |
| `RECORDING_INPUT_HOST_DIR` | 아니요 | `${DATA_ROOT}/inbox` | Compose가 입력 폴더에 연결할 호스트 경로 |
| `TRANSCRIPT_HOST_DIR` | 아니요 | `${DATA_ROOT}/transcripts` | Compose가 transcript 폴더에 연결할 호스트 경로 |
| `SPEAKER_ROOT` | 예 | `/data/speakers` | 화자 클립/프로필 저장 루트 |
| `SUMMARY_ROOT` | 예 | `/data/documents` | 범주별 요약 저장 루트 |
| `APP_DATA_DIR` | 예 | `/data/app` | SQLite와 격리 파일 저장 루트 |
| `SCAN_INTERVAL_SECONDS` | 아니요 | `10` | 입력 폴더 재검색 간격 |
| `FILE_STABLE_SECONDS` | 아니요 | `30` | 크기·수정 시간이 변하지 않아야 하는 시간 |
| `WHISPER_MODEL` | 아니요 | `large-v3` | STT 모델; 운영 기본값은 고정 |
| `WHISPER_DEVICE` | 아니요 | `cuda` | 실제 모델 실행 장치 |
| `WHISPER_COMPUTE_TYPE` | 아니요 | `float16` | 장비에 맞춘 연산 타입 |
| `WHISPER_LANGUAGE` | 아니요 | 빈 값 | 빈 값이면 자동 감지, 필요하면 `ko` |
| `HF_TOKEN` | 예 | 비공개 | 권한이 필요한 pyannote 모델 접근 토큰 |
| `SPEAKER_AUTO_MATCH_THRESHOLD` | 아니요 | 보정 후 결정 | 이 점수 이상일 때만 자동 식별 |
| `SPEAKER_MATCH_MARGIN` | 아니요 | 보정 후 결정 | 1위와 2위 후보의 최소 점수 차이 |
| `CATEGORIES` | 아니요 | `강의,일상 대화,회의,게임 목록,기타` | 허용할 대분류 목록 |
| `AUTO_SUMMARY_CATEGORIES` | 아니요 | `강의,회의` | 자동 요약할 범주 목록 |
| `LLM_PROVIDER` | 예 | `openai_compatible` | 분류/요약 공급자 선택 |
| `LLM_BASE_URL` | 공급자별 | 로컬 또는 원격 URL | OpenAI 호환 API 주소 |
| `LLM_API_KEY` | 공급자별 | 비공개 | API 키 |
| `LLM_MODEL` | 예 | 공급자 모델명 | 분류/요약에 사용할 모델 |
| `APP_BIND_HOST` | 아니요 | `0.0.0.0` | 디스플레이 없는 서버에서 `web` 서비스를 노출할 주소 |
| `APP_PORT` | 아니요 | `38000` | 브라우저에서 접속할 `web` 포트 |
| `LOG_LEVEL` | 아니요 | `INFO` | 로그 수준 |

경로, 범주 목록, 자동 요약 목록, 임계값은 시작할 때 한 번 검증한다. 범주 목록에 없는 자동 요약 범주가 있거나 경로가 서로 위험하게 중첩되면 시작을 실패시켜 잘못된 운영을 막는다.

## 8. 데이터 모델

SQLite가 “어디까지 처리되었는가”의 단일 기준이다. 단순히 출력 파일이 존재한다는 이유로 단계를 건너뛰지 않는다. 다만 DB 복구가 필요할 때를 위해 각 JSON 결과물에는 녹음 ID, 콘텐츠 해시, 생성 시각, 스키마 버전을 기록한다.

### 8.1 핵심 테이블

#### `recordings`

| 필드 | 의미 |
|---|---|
| `id` | 내부 UUID |
| `content_sha256` | 중복 식별 키, unique |
| `source_path` | 현재 관찰된 원본 경로 |
| `original_name` | 최초 파일명 |
| `size_bytes` | 발견 당시 크기 |
| `duration_ms` | ffprobe로 확인한 길이 |
| `recorded_at` | 미디어 메타데이터 또는 파일 시각 |
| `status` | 현재 파이프라인 상태 |
| `category` | 확정된 대분류, 아직 없으면 null |
| `category_confidence` | 모델이 반환한 신뢰도 |
| `needs_speaker_review` | 사용자 검토 필요 여부 |
| `last_error_code` | 기계가 처리할 실패 코드 |
| `last_error_message` | 사용자가 볼 실패 설명 |
| `created_at`, `updated_at` | 감사용 시각 |

#### `segments`

| 필드 | 의미 |
|---|---|
| `id` | 발화 구간 ID |
| `recording_id` | 녹음 ID |
| `start_ms`, `end_ms` | 구간 시간 |
| `text` | STT 텍스트 |
| `local_speaker_id` | 이 녹음 안의 `SPEAKER_00` |
| `person_id` | 실제 인물, 미확정이면 null |
| `speaker_source` | `manual`, `auto`, `unresolved` |
| `speaker_score` | 자동 연결 점수 |
| `revision` | 수정 충돌 방지용 증가 값 |

#### `recording_speakers`

녹음 안에서 발견된 임시 화자를 나타낸다. 대표 클립, 임베딩 위치, 후보와 확정 상태를 기록한다.

#### `persons`

사용자가 정의한 실제 화자다. `display_name`은 UI 표시용이며 같은 이름을 허용하되 ID로 구분한다.

#### `speaker_embeddings`

수동 확정된 깨끗한 구간의 임베딩과 출처를 기록한다. 사용자가 연결을 취소한 구간은 프로필 계산에서 제외한다.

#### `jobs`

| 필드 | 의미 |
|---|---|
| `id` | 작업 ID |
| `recording_id` | 대상 녹음 |
| `kind` | `transcribe`, `finalize_speakers`, `classify`, `summarize`, `render` |
| `status` | `queued`, `running`, `succeeded`, `failed` |
| `attempts` | 시도 횟수 |
| `available_at` | 다음 재시도 가능 시각 |
| `locked_at` | worker 점유 시각 |
| `error_code`, `error_message` | 실패 정보 |
| `created_at`, `updated_at` | 작업 시각 |

동일 녹음에 같은 종류의 활성 작업이 둘 이상 생기지 않도록 부분 unique 규칙 또는 등록 트랜잭션으로 막는다.

#### `artifacts`

생성된 transcript, 대표 클립, summary의 경로·해시·스키마 버전·생성 시각을 기록한다.

#### `audit_events`

화자 수정, 범주 수정, 요약 재요청처럼 결과에 영향을 주는 사용자 동작과 자동 결정을 기록한다. 디버깅과 재생성 근거에 필요한 최소 정보만 보존한다.

### 8.2 ID와 시간 규칙

- 내부 ID는 UUID를 사용한다.
- DB 시간은 UTC ISO 8601로 저장하고 UI에서 로컬 시간대로 표시한다.
- 오디오 구간은 부동소수 초가 아니라 정수 밀리초로 저장한다.
- 사용자에게 보이는 파일명은 `<날짜>-<원본 stem>-<짧은 recording_id>`처럼 충돌 없는 형태를 사용할 수 있으나, 내부 참조는 UUID만 사용한다.

## 9. 처리 상태와 전이

### 9.1 녹음 상태

```text
DISCOVERED
  -> TRANSCRIBING
  -> SPEAKER_REVIEW | CLASSIFYING
  -> READY_FOR_SUMMARY | SUMMARIZING
  -> COMPLETED

어느 실행 상태에서든 복구 가능한 오류 -> FAILED
FAILED에서 재시도 -> 실패한 단계 직전의 안전한 상태
```

| 상태 | 의미 | 다음 전이 조건 |
|---|---|---|
| `DISCOVERED` | 안정화·검증·해시 계산이 끝나 DB에 등록됨 | STT 작업 등록 |
| `TRANSCRIBING` | STT/정렬/화자 분리 진행 중 | 결과 저장 성공 |
| `SPEAKER_REVIEW` | 미확정 또는 저신뢰 화자가 있음 | 모든 화자 검토 완료 |
| `CLASSIFYING` | 전체 문서 분류 중 | 허용 범주의 결과 저장 |
| `READY_FOR_SUMMARY` | 자동 요약 대상이 아니며 수동 요청 가능 | 사용자 요약 요청 또는 완료 처리 |
| `SUMMARIZING` | 요약 생성 중 | 결과 검증 및 저장 성공 |
| `COMPLETED` | 현재 입력과 사용자 수정에 맞는 결과가 모두 최신 | 수정 시 필요한 이전 상태로 이동 |
| `FAILED` | 자동 재시도 한도를 넘었거나 사용자 조치 필요 | 원인 해소 후 재시도 |

자동 요약 대상이 아닌 녹음은 분류와 최종 transcript 렌더가 끝나면 `COMPLETED`로 표시하되, UI에 “요약 없음/요청 가능”을 별도 표시한다. `READY_FOR_SUMMARY`는 요약 요청을 대기하는 영구 상태가 아니라 분류 직후 정책 판단을 표현하는 짧은 상태로 사용한다.

### 9.2 수정에 따른 무효화 규칙

| 변경 | 다시 만들어야 하는 것 | 다시 하지 않는 것 |
|---|---|---|
| 화자 표시 이름 변경 | transcript Markdown, 기존 summary | STT, diarization, 분류 |
| 발화 구간 화자 변경 | transcript JSON/Markdown, 기존 summary | STT 텍스트, 보통의 대분류 |
| 발화 구간 경계 변경 | 대표 클립, 임베딩, transcript, 분류, summary | 원본 STT가 재사용 가능하면 STT |
| transcript 텍스트 수정 | transcript, 분류, summary | 오디오 분석 |
| 범주 수동 변경 | transcript 메타데이터, summary 경로/내용 | STT, 화자 처리 |
| 요약 정책 변경 | 해당 범주의 누락 요약 작업 | STT, 화자, 분류 |

수정 시 결과물을 바로 덮어쓰지 않고 DB에 수정과 revision을 먼저 커밋한 뒤 `render` 또는 `summarize` 작업을 등록한다. API에는 기대 revision을 보내게 하여 오래 열린 화면이 최신 수정 내용을 덮어쓰지 못하게 한다.

## 10. 단계별 상세 처리

### 10.1 입력 발견

worker는 `SCAN_INTERVAL_SECONDS`마다 입력 폴더를 재귀 검색한다. 첫 버전에서 허용하는 확장자는 `.m4a`이며 대소문자를 무시한다.

파일은 다음 조건을 모두 만족할 때만 처리 대상으로 본다.

1. 일반 파일이며 심볼릭 링크가 아니다.
2. 임시 파일명 패턴이 아니다.
3. 크기와 수정 시간이 `FILE_STABLE_SECONDS` 동안 변하지 않았다.
4. ffprobe로 컨테이너와 오디오 스트림을 읽을 수 있다.
5. 크기가 0보다 크고 오디오 길이가 0보다 길다.

그 후 스트리밍 방식으로 SHA-256을 계산한다.

- 기존 해시가 없으면 `recordings`를 만들고 STT 작업을 하나 등록한다.
- 기존 해시가 있으면 새 경로만 관찰 정보로 남기고 처리 작업을 만들지 않는다.
- 같은 경로의 내용이 바뀌면 새 해시이므로 새 녹음으로 취급한다.
- 읽을 수 없는 파일은 즉시 삭제하지 않고 실패 사유를 남긴다. 일정 시간 계속 불완전한 파일은 UI에서 격리하도록 안내한다.

### 10.2 미디어 표준화

WhisperX 입력 전에 FFmpeg로 모델이 안정적으로 읽는 mono PCM 16 kHz 임시 WAV를 만든다. 이 파일은 재생성 가능한 작업 임시물이며 성공 후 삭제할 수 있다. 원본 `.m4a`는 그대로 보존한다.

명령 실행은 인자 배열을 사용하고 shell 문자열을 조합하지 않는다. 경로의 공백과 특수문자를 안전하게 다루며, 제한 시간을 넘기거나 종료 코드가 0이 아니면 구조화된 오류를 남긴다.

### 10.3 STT, 정렬, 화자 분리

하나의 `transcribe` 작업에서 다음 순서로 실행한다.

1. WhisperX `large-v3`로 전사한다.
2. 언어별 alignment 모델로 단어 시간 정보를 보정한다.
3. pyannote로 화자 구간을 구한다.
4. WhisperX의 화자 할당으로 텍스트 segment에 임시 화자를 연결한다.
5. 정규화된 segment를 DB와 `transcript.json`에 저장한다.

원시 모델 응답 전체에 애플리케이션이 의존하지 않도록 아래 형태로 정규화한다.

```json
{
  "schema_version": 1,
  "recording_id": "uuid",
  "content_sha256": "...",
  "language": "ko",
  "segments": [
    {
      "id": "uuid",
      "start_ms": 1250,
      "end_ms": 4820,
      "local_speaker_id": "SPEAKER_00",
      "person_id": null,
      "speaker_name": null,
      "text": "안녕하세요. 회의를 시작하겠습니다."
    }
  ]
}
```

긴 녹음 때문에 GPU 메모리가 부족할 수 있으므로 batch size는 환경과 장비 기준으로 조절 가능하게 하되, 첫 구현에서는 자동 튜닝 로직을 만들지 않는다. OOM 발생 시 작업을 실패 처리하고 운영자가 값을 낮춘 뒤 재시도한다.

### 10.4 화자 대표 구간과 임베딩

각 임시 화자에 대해 다음 기준으로 대표 구간을 고른다.

- 너무 짧거나 겹침 발화가 많은 구간은 제외한다.
- 무음과 배경 소음 비율이 높은 구간은 제외한다.
- 가능한 경우 서로 떨어진 2~3개 구간을 선택한다.
- 대표 구간은 UI에서 빠르게 들을 수 있는 짧은 오디오 클립으로 저장한다.

임베딩은 대표 구간별로 저장하고 비교 점수는 여러 구간의 중앙값처럼 이상치에 덜 민감한 집계를 사용한다. 한 개의 짧은 클립만으로 자동 확정하지 않는다.

### 10.5 화자 자동 식별

각 임시 화자의 임베딩을 기존 `persons` 프로필과 비교한다.

자동 연결은 아래 두 조건을 모두 만족할 때만 수행한다.

```text
best_score >= SPEAKER_AUTO_MATCH_THRESHOLD
best_score - second_best_score >= SPEAKER_MATCH_MARGIN
```

추가 안전 규칙은 다음과 같다.

- 비교 가능한 음성이 부족하면 수동 검토로 보낸다.
- 같은 녹음의 서로 다른 임시 화자를 기본적으로 같은 인물에 자동 연결하지 않는다.
- 사용자가 과거에 연결을 명시적으로 거부한 후보는 자동 연결하지 않는다.
- 모델 또는 전처리 버전이 달라진 임베딩은 섞어 비교하지 않는다.
- 점수와 후보 목록을 보존해 자동 결정의 근거를 확인할 수 있게 한다.

임계값 기본값은 임의로 확정하지 않는다. 실제 사용자 음성 표본으로 같은 사람/다른 사람 점수 분포를 측정한 뒤, 오탐을 낮추는 방향으로 설정한다. 표본이 충분하지 않은 초기에는 자동 연결을 끄거나 매우 보수적인 값으로 시작한다.

### 10.6 사용자 화자 검토

미확정 화자가 하나라도 있으면 녹음은 `SPEAKER_REVIEW` 상태가 된다. 검토 화면은 다음 정보를 제공한다.

- 원본 파일명과 녹음 일시
- `SPEAKER_00`별 발화량과 대표 클립
- 자동 후보 이름, 점수, 1·2위 점수 차이
- 기존 인물 선택
- 새 인물 생성
- “알 수 없음”으로 확정
- 전체 발화 목록과 개별 발화의 화자 변경

사용자가 한 임시 화자를 실제 인물에 연결하면 관련 segment에 반영한다. 개별 segment만 다른 인물로 수정하는 것도 허용한다. 수동 확정된 깨끗한 구간만 향후 자동 식별 프로필에 추가한다.

### 10.7 문서 분류

화자 검토가 끝나면 전체 transcript를 기준으로 하나의 대분류를 선택한다. 기본 범주는 다음과 같다.

- 강의
- 일상 대화
- 회의
- 게임 목록
- 기타

분류 프롬프트에는 허용 범주와 각 범주의 짧은 판정 기준을 제공하고, 모델 출력은 구조화된 JSON으로 제한한다.

```json
{
  "category": "회의",
  "confidence": 0.91,
  "reason": "여러 화자가 안건, 결정 사항, 후속 작업을 논의함"
}
```

- `category`가 허용 목록에 없으면 결과를 거부하고 한 번 교정 요청한다.
- 그래도 실패하면 `기타`로 조용히 바꾸지 않고 작업을 실패시킨다.
- 낮은 신뢰도는 UI에 검토 필요로 표시하되, 첫 버전에서는 분류 확인 때문에 전체 파이프라인을 무조건 중단하지 않는다.
- 사용자는 범주를 수정할 수 있고 수동 선택이 자동 결과보다 우선한다.
- 긴 문서는 segment를 임의로 일부 샘플링하지 않는다. 공급자의 컨텍스트 한도를 넘으면 부분별 핵심 주제를 추출한 뒤 전체 분류를 한 번 수행한다.

### 10.8 transcript 문서 생성

`transcript.md`는 최소한 다음 구조를 갖는다.

```markdown
# 녹음 제목

- 녹음 일시: ...
- 원본 파일: ...
- 범주: 회의
- 처리 시각: ...

## 전체 내용

**[00:01:02] 김민수**
안녕하세요. 회의를 시작하겠습니다.
```

화자가 미확정이면 `미확정(SPEAKER_00)`으로 표시한다. transcript JSON에는 원본 정밀도를 보존하고 Markdown은 사람이 읽기 좋은 길이로 인접 발화를 합칠 수 있다.

### 10.9 요약 정책과 생성

분류 결과가 `AUTO_SUMMARY_CATEGORIES`에 포함되면 worker가 자동으로 `summarize` 작업을 등록한다. 포함되지 않으면 사용자가 UI/API에서 요청할 수 있다. 같은 recording revision에 대한 활성 또는 성공한 요약 작업이 있으면 중복 등록하지 않는다.

요약 형식은 범주별로 다르게 하되 첫 버전에서는 코드에 명시된 소수의 템플릿을 사용한다.

| 범주 | 기본 요약 구조 |
|---|---|
| 강의 | 핵심 주제, 개념 정리, 예시, 복습 항목 |
| 회의 | 목적, 논의 내용, 결정 사항, 담당자·기한이 있는 할 일, 미해결 사항 |
| 일상 대화 | 주요 화제, 합의/약속, 기억할 사항 |
| 게임 목록 | 언급된 게임, 선호/평가, 후속 확인 항목 |
| 기타 | 핵심 요약, 주요 사실, 후속 항목 |

모델이 transcript에 없는 담당자, 날짜, 결정을 만들어내지 않도록 다음 규칙을 프롬프트와 출력 검증에 포함한다.

- 근거가 없으면 “확인되지 않음”으로 표시한다.
- 직접 인용은 필요한 최소 범위로 제한하고 timestamp를 연결한다.
- 할 일은 담당자·기한·내용을 각각 nullable 필드로 반환한다.
- 요약 JSON을 먼저 검증한 뒤 Markdown으로 렌더한다.

요약 결과는 다음 위치에 저장한다.

```text
${SUMMARY_ROOT}/<category_slug>/요약/<recording_id>.json
${SUMMARY_ROOT}/<category_slug>/요약/<recording_id>.md
```

`category_slug`는 코드에서 안전한 경로 조각으로 변환하며 `/`, `..`, 제어 문자를 허용하지 않는다. 표시용 한글 범주 이름과 경로 slug의 매핑을 메타데이터에 남긴다.

## 11. 프런트엔드 UX와 API 계약

프런트엔드는 단순 상태 조회 화면이 아니라 화자 학습 데이터의 품질을 결정하는 작업 도구다. 자동 추론의 결과와 사용자가 확정한 결과를 시각적으로 구분하고, 저장되지 않은 수정이나 충돌을 숨기지 않는 것을 기본 원칙으로 한다.

### 11.1 화면과 경로

| 경로 | 화면 | 필수 기능 |
|---|---|---|
| `/` | 대시보드 | 상태별 개수, 화자 검토 대기, 실패, 최근 녹음, 실행 중 작업 |
| `/recordings/:id` | 녹음 상세 | 메타데이터, 오디오, transcript, 범주 수정, 요약 요청/결과, 처리 이력 |
| `/recordings/:id/speakers` | 화자 검토 | 임시 화자별 대표 클립, 후보, 인물 연결, 발화별 화자 수정 |
| `/people` | 인물 관리 | 인물 목록, 이름 수정, 연결된 녹음 확인; 병합/삭제는 첫 버전 제외 |
| `/failures/:recordingId` | 실패 상세 | 오류 코드, 사용자용 설명, 실패 단계, 재시도 |

### 11.2 화자 검토 핵심 흐름

화자 검토 화면은 다음 흐름으로 동작한다.

1. 화면 상단에서 원본 녹음, 처리 상태, 미확정 화자 수를 확인한다.
2. 임시 화자 카드를 선택하고 2~3개의 대표 클립을 재생한다.
3. 기존 인물 후보를 점수와 함께 선택하거나 새 인물을 생성하거나 `알 수 없음`으로 확정한다.
4. transcript에서 해당 화자의 발화가 강조된다.
5. 잘못 분리된 개별 발화는 행 단위 선택으로 다른 인물에 다시 배정한다.
6. 변경 요약을 확인한 뒤 한 번에 저장한다.
7. API가 새 revision과 재생성 작업을 반환하면 화면은 이를 표시하고 최신 상태를 polling한다.

UI는 다음 규칙을 지킨다.

- 자동 확정, 사용자 확정, 미확정을 색상뿐 아니라 텍스트와 아이콘으로 함께 구분한다.
- 후보 점수는 숨기지 않되 “신원 인증 점수”로 오해하지 않도록 유사도라고 표시한다.
- 발화 행의 timestamp를 누르면 전체 녹음 플레이어가 해당 시점으로 이동한다.
- 대표 클립은 브라우저 기본 `<audio controls>`를 우선 사용한다.
- 첫 버전에서는 파형 편집기나 drag 기반 구간 편집기를 넣지 않는다. 화자 배정 수정에 집중한다.
- 여러 발화를 선택해 같은 인물로 일괄 변경할 수 있게 한다.
- 저장 전에는 실제 DB를 바꾸지 않고, 화면 이탈 시 저장되지 않은 변경을 경고한다.
- 409 revision 충돌이 발생하면 자동 덮어쓰지 않고 최신 데이터를 불러와 사용자가 다시 확인하게 한다.
- 작업 저장 중 버튼 중복 클릭을 막고, 성공/실패 결과를 화면에 명확히 알린다.

### 11.3 상태 조회와 갱신

- 대시보드와 실행 중인 녹음 상세는 3~5초 간격 polling으로 갱신한다.
- 완료되거나 실패한 항목만 보이는 화면에서는 polling을 중단한다.
- 브라우저 탭이 보이지 않을 때는 polling 빈도를 낮추거나 멈춘다.
- API 오류가 나면 마지막 성공 데이터를 현재 데이터처럼 조용히 유지하지 않고 “갱신 실패” 상태를 표시한다.
- 로딩, 빈 목록, 권한/연결 오류, 404, 409, 422, 500 상태마다 사용자가 취할 수 있는 다음 행동을 제공한다.

### 11.4 접근성과 반응형 기준

- 모든 입력은 연결된 label을 갖고 키보드만으로 조작할 수 있어야 한다.
- 재생, 저장, 재시도처럼 중요한 버튼에는 접근 가능한 이름을 제공한다.
- focus 표시를 제거하지 않는다.
- 상태는 색상에만 의존하지 않는다.
- 데스크톱을 주 작업 환경으로 설계하되, 휴대폰에서도 대시보드 확인과 간단한 화자 연결이 가능해야 한다.
- 긴 transcript는 페이지 전체를 한 번에 무겁게 렌더하지 않고 페이지네이션 또는 단순한 구간 단위 로딩을 사용한다.

### 11.5 최소 API

| 메서드/경로 | 역할 |
|---|---|
| `GET /health/live` | 프로세스 생존 확인 |
| `GET /health/ready` | DB와 필수 경로 사용 가능 여부 |
| `GET /api/recordings` | 상태/범주별 녹음 목록 |
| `GET /api/recordings/{id}` | 녹음, segment, artifact 상세 |
| `GET /api/recordings/{id}/segments` | 페이지 단위 발화 목록과 revision |
| `POST /api/recordings/{id}/retry` | 실패 단계 재시도 |
| `PATCH /api/recordings/{id}/category` | 범주 수동 수정 |
| `POST /api/recordings/{id}/summary` | 수동 요약 요청 |
| `PUT /api/recordings/{id}/speakers/{local_id}` | 임시 화자를 인물에 연결 |
| `PATCH /api/segments/{id}/speaker` | 개별 발화 화자 수정 |
| `PATCH /api/segments/speakers` | 선택한 여러 발화의 화자 일괄 수정 |
| `GET /api/persons` | 기존 인물과 후보 선택용 목록 |
| `POST /api/persons` | 실제 화자 생성 |
| `PATCH /api/persons/{id}` | 인물 표시 이름 수정 |
| `GET /api/media/{artifact_id}` | 권한 검증 후 녹음/대표 클립 stream 제공 |

쓰기 API는 현재 `revision`을 요구하고, 성공 시 새 revision과 등록된 후속 작업을 반환한다. 존재하지 않는 녹음은 404, revision 충돌은 409, 상태상 불가능한 전이는 422로 응답한다.

브라우저의 오디오 seek가 동작하도록 media endpoint는 유효한 `Range` 요청에 `206 Partial Content`, `Content-Range`, `Accept-Ranges`를 올바르게 반환해야 한다. artifact ID가 설정된 오디오 루트 밖을 가리키거나 허용되지 않은 종류이면 404로 처리한다.

API 오류는 프런트엔드가 일관되게 표시할 수 있도록 아래 최소 구조를 사용한다.

```json
{
  "error": {
    "code": "REVISION_CONFLICT",
    "message": "다른 변경이 먼저 저장되었습니다.",
    "details": {"current_revision": 8}
  }
}
```

FastAPI의 OpenAPI schema를 API 계약의 기준으로 삼는다. 프런트엔드의 요청/응답 타입은 이 schema에서 생성하거나 검증하여, 백엔드 응답이 바뀌었는데 화면 타입만 과거 상태로 남는 것을 병합 전에 탐지한다.

### 11.6 프런트엔드 제공과 접근 범위

운영 빌드는 Nginx가 React 정적 파일을 제공하고 `/api/*`를 내부 `api` 서비스로 전달한다. 브라우저에는 하나의 origin만 보이므로 운영 CORS 설정은 필요 없다. 클라이언트 라우트는 새로고침해도 `index.html`로 fallback해야 하지만 `/api` 오류를 HTML로 바꾸면 안 된다.

개발 시 Vite dev server가 `/api`를 FastAPI로 proxy한다. API 주소를 컴포넌트 곳곳에 넣지 않고 하나의 fetch client에서 상대 경로로 호출한다.

첫 버전은 디스플레이 없는 서버에서 접근할 수 있도록 `0.0.0.0:38000` 바인딩을 기본으로 한다.
인증 시스템은 포함하지 않으므로 신뢰할 수 있는 LAN과 호스트 방화벽 안에서만 사용한다. 인터넷에
노출하려면 구현 범위 밖의 리버스 프록시 인증과 TLS를 먼저 구성해야 한다. 오디오 파일 경로를 API
응답에 그대로 노출하지 않고 artifact ID로 조회한다.

## 12. 중복 방지, 재시도, 복구

### 12.1 멱등성 키

| 작업 | 멱등성 기준 |
|---|---|
| 입력 등록 | `content_sha256` |
| STT | `recording_id + audio_hash + speech_config_version` |
| 분류 | `recording_id + transcript_revision + classifier_version` |
| 요약 | `recording_id + transcript_revision + category + summary_template_version` |
| 렌더 | `recording_id + document_revision + renderer_version` |

### 12.2 재시도 정책

- 일시적인 API 제한, 네트워크 오류, 모델 서버 일시 장애는 지수 backoff로 최대 3회 자동 재시도한다.
- 잘못된 입력, 토큰 권한 부족, 허용되지 않은 분류 출력, GPU OOM처럼 설정/사용자 조치가 필요한 오류는 즉시 `FAILED`로 둔다.
- worker가 종료되어 `running` 작업의 lock이 오래된 경우 시작 시 `queued`로 회수한다.
- 이미 성공한 단계의 입력·설정 버전이 같으면 재실행하지 않는다.
- 사용자가 재시도를 누르면 실패 횟수를 지우는 대신 새 시도 이력을 남긴다.

### 12.3 장애 시 보존 원칙

- DB 커밋 전에 완성되지 않은 파일은 최종 artifact로 등록하지 않는다.
- 파일 생성 성공 후 DB 등록 실패 시 다음 복구 스캔이 해시를 확인해 등록하거나 다시 안전하게 덮어쓴다.
- DB 백업은 API/worker를 내리거나 SQLite online backup 방식으로 수행한다.
- 백업 대상은 `app.db`, 원본 녹음, transcript JSON, 화자 프로필이다. Markdown은 재생성 가능하지만 운영 편의를 위해 함께 백업한다.

## 13. 로그와 운영 관측

로그는 구조화된 한 줄 형식으로 stdout에 출력하여 `docker compose logs`로 확인할 수 있게 한다.

필수 필드:

- timestamp
- level
- service
- event
- recording_id/job_id(해당하는 경우)
- stage
- attempt
- duration_ms(완료 이벤트)
- error_code(실패 이벤트)

비밀값, 전체 transcript, 전체 프롬프트, 원본 오디오는 로그에 남기지 않는다. 사용자 화면에는 기술 stack trace 대신 조치 가능한 설명을 표시하고, stack trace는 서버 로그에만 남긴다.

첫 버전에서 별도 Prometheus를 추가하지 않는다. 대시보드에 DB에서 계산한 대기/진행/실패 작업 수와 최근 처리 시간을 보여주는 것으로 시작한다.

## 14. 보안과 개인정보

- `.env`, 모델 토큰, LLM API 키는 Git에 커밋하지 않는다.
- 컨테이너는 가능한 비-root 사용자로 실행한다.
- 입력/출력 볼륨은 필요한 서비스에만 마운트하고, API에는 입력 폴더 쓰기 권한을 주지 않는다.
- 파일 경로는 설정된 루트 하위인지 확인한 뒤 접근한다.
- 업로드 파일명을 shell 명령이나 결과 경로에 직접 삽입하지 않는다.
- 외부 LLM을 사용하면 transcript가 외부로 전송될 수 있음을 README와 UI 설정 화면에 명시한다.
- 완전 로컬 처리가 필요하면 OpenAI 호환 로컬 모델 서버를 사용하고 외부 송신이 없는지 별도로 검증한다.
- 원본/파생 음성의 보관 기간과 삭제는 오삭제 위험이 있으므로 첫 버전에서 자동화하지 않는다.

## 15. 개발 순서

각 단계는 이전 단계의 검증을 통과한 뒤 진행한다. 백엔드 전체를 만든 뒤 마지막에 화면을 얹는 방식은 API와 사용자 흐름의 불일치를 늦게 발견하게 한다. 따라서 실제 대형 모델은 뒤로 미루되, 가짜 AI 어댑터를 사용해 API와 프런트엔드가 함께 동작하는 작은 수직 흐름을 먼저 닫는다.

### 0단계: 프로젝트 골격과 실행 기준

**구현**

- Python 백엔드와 React/TypeScript 프런트엔드 프로젝트 생성
- 설정 로더, 로깅, 백엔드/프런트엔드 Dockerfile, Compose 작성
- `.env.example` 작성
- `api`/`worker`는 같은 백엔드 이미지로, `web`은 정적 프런트엔드 이미지로 기동하도록 구성
- liveness/readiness endpoint 구현
- React 라우팅, 공통 오류 표시, API fetch client의 최소 골격 구현

**완료 기준**

- 필수 환경 변수가 없으면 변수명을 포함한 오류로 시작이 중단된다.
- 유효한 임시 디렉터리 설정에서는 세 서비스가 시작된다.
- `docker compose config`가 성공한다.
- readiness가 DB와 모든 필수 경로를 확인한다.
- 브라우저에서 `/`를 열 수 있고, `web`을 통한 `/api/health/ready` 요청이 성공한다.

### 1단계: DB와 입력 감지

**구현**

- SQLite 스키마와 최소 마이그레이션 방식
- 안정 파일 판정, ffprobe 검사, SHA-256 중복 방지
- `recordings`와 `jobs` 등록
- 단일 worker lock/재시도 기반

**완료 기준**

- 쓰는 중인 파일은 등록하지 않는다.
- 완성된 유효 m4a는 정확히 한 번 등록한다.
- 같은 바이트의 다른 파일명은 새 STT 작업을 만들지 않는다.
- 재시작 후에도 성공한 입력을 다시 처리하지 않는다.

### 2단계: 가짜 어댑터로 끝까지 흐름 연결

**구현**

- 고정된 transcript/화자/분류/요약을 반환하는 테스트 어댑터
- 상태 전이, artifact 원자적 쓰기, 자동/수동 요약 정책
- 실패 주입과 재시도
- 최소 대시보드와 녹음 상세 화면
- OpenAPI 계약과 프런트엔드 타입 연결

**완료 기준**

- 작은 fixture 하나가 발견부터 `COMPLETED`까지 간다.
- 각 결과 JSON/Markdown이 예상 경로와 schema로 생성된다.
- 중간 단계 실패 후 재시도해도 중복 artifact/job이 없다.
- 브라우저에서 fixture의 상태 변화, transcript, 분류, 요약을 확인할 수 있다.
- 백엔드 schema와 프런트엔드 API 타입이 어긋나면 검증이 실패한다.

이 단계가 중요한 이유는 GPU 모델과 LLM의 느리고 불안정한 요소를 제외한 상태 관리 오류를 먼저 잡기 위해서다.

### 3단계: 실제 STT와 화자 분리

**구현**

- FFmpeg 표준화
- WhisperX large-v3 전사와 alignment
- pyannote diarization과 segment 화자 할당
- 실제 모델 버전/설정 fingerprint 저장

**완료 기준**

- 한국어 단일 화자, 다중 화자, 짧은 무음 포함 fixture가 처리된다.
- 모든 segment의 시간이 유효하고 오디오 길이를 벗어나지 않는다.
- segment가 시작 시간 순이며 끝 시간이 시작보다 크다.
- GPU OOM과 모델 권한 오류가 구분된 오류 코드로 보인다.

### 4단계: 화자 검토와 프로필

**구현**

- 대표 클립 생성과 안전한 재생
- 화자 검토 React 화면과 오디오 seek 동작
- 인물 생성, 임시 화자 연결, 개별/일괄 segment 수정
- embedding 저장, 후보 점수, 수동 검토 흐름
- 수정에 따른 transcript/summary 무효화

**완료 기준**

- 새 화자를 만들고 한 녹음의 `SPEAKER_00`에 연결할 수 있다.
- 잘못 배정된 segment 하나만 다른 화자로 바꿀 수 있다.
- 수정 이후 JSON/Markdown과 UI가 같은 값을 표시한다.
- 오래 열린 화면의 수정은 revision 409로 거부된다.
- 키보드만으로 대표 클립 재생, 후보 선택, 저장이 가능하다.
- 저장되지 않은 변경이 있을 때 화면을 벗어나면 경고한다.

### 5단계: 보수적 화자 자동 식별

**구현**

- 수동 확정 자료로 인물별 프로필 계산
- 1위 임계값과 1·2위 margin 적용
- 거부 후보/모델 버전 호환 규칙
- 자동 결정 근거 표시

**완료 기준**

- 알려진 동일 화자, 다른 화자, 애매한 표본으로 평가표를 만든다.
- 애매한 표본은 자동 확정하지 않는다.
- 임계값은 평가 자료와 함께 기록한다.
- 자동 연결 결과를 수동으로 취소하고 재학습 자료에서 제외할 수 있다.

### 6단계: 분류와 문서 생성

**구현**

- 허용 범주 기반 구조화 분류
- 긴 transcript 처리
- 상세 화면의 범주 표시와 수동 수정
- versioned transcript JSON/Markdown 렌더링

**완료 기준**

- 대표 예시가 허용된 큰 범주로만 분류된다.
- 알 수 없는 범주, 깨진 JSON, timeout이 안전하게 실패한다.
- 범주 수정 후 표시와 artifact 메타데이터가 일치한다.

### 7단계: 자동/수동 요약

**구현**

- 범주별 summary schema와 템플릿
- 자동 요약 정책, 상세 화면의 수동 요청, 중복 클릭 방지
- category slug 안전성
- 수정 시 stale summary 재생성

**완료 기준**

- 자동 대상 범주는 별도 동작 없이 요약된다.
- 비대상 범주는 요청 전 요약되지 않고 요청 후 한 번 생성된다.
- 결과가 `${SUMMARY_ROOT}/<범주>/요약/` 규칙을 따른다.
- 화자/텍스트/범주 수정 후 이전 요약이 최신인 것처럼 남지 않는다.

### 8단계: 운영 UX 완성과 실패 복구

**구현**

- 대시보드 필터, 실패/재시도 화면, loading/empty/error 상태 완성
- 반응형 레이아웃, 키보드 탐색, focus, 상태의 비색상 표현 점검
- stale job 회수, 오류 분류, 로그 상관관계 ID
- DB/결과물 백업·복원 절차 문서

**완료 기준**

- 사용자가 CLI 없이 대기, 검토, 실패, 완료 상태를 구분할 수 있다.
- 실패 원인과 가능한 조치를 확인하고 재시도할 수 있다.
- worker 강제 종료 후 재시작해 진행 중 작업이 안전하게 회수된다.
- 핵심 GUI 흐름이 실제 브라우저 E2E 테스트로 통과한다.

### 9단계: 실제 환경 인수 시험

**구현**

- 실제 Syncthing 폴더 연결
- 실사용 녹음 표본 처리
- 화자 threshold와 batch size 보정
- 운영 README 확정

**완료 기준**

- 아래 20개의 인수 시나리오가 모두 통과한다.
- Compose 재시작과 호스트 재부팅 후 중복·유실이 없다.
- 사용자가 새 화자 검토부터 요약 확인까지 혼자 수행할 수 있다.

## 16. 일관된 검증 프로세스

모든 개발 단계와 모든 변경은 같은 검증 루프를 따른다. 모델 결과처럼 완전히 결정적이지 않은 부분도 “느낌상 맞음”이 아니라 구조·불변식·고정 평가 자료로 검증한다.

### 16.1 변경 단위 검증 루프

1. **요구사항 연결**
   변경이 이 문서의 어느 목표·완료 기준을 충족하는지 작업 설명에 적는다. 연결되는 기준이 없으면 구현 필요성을 다시 확인한다.

2. **위험과 불변식 정의**
   변경 전에 깨지면 안 되는 것을 1~3개 적는다. 예: “동일 해시는 STT job이 하나다”, “수동 화자 선택은 자동 선택보다 우선한다.”

3. **가장 작은 자동 검증 작성**
   비결정적 외부 모델은 가짜 어댑터로 고정하고, 상태 전이·경로·중복·오류 처리를 먼저 테스트한다. 프런트엔드 변경은 사용자 행동과 화면 결과로 검증한다. 버그 수정은 재현 테스트가 먼저 실패하고 수정 후 통과해야 한다.

4. **구현 후 빠른 검사**
   포맷, lint, 타입 검사, 해당 단위 테스트를 실행한다. 실패가 있으면 다음 단계로 가지 않는다.

5. **통합 검사**
   임시 SQLite와 임시 디렉터리, 작은 fixture를 사용해 API/worker/파일 결과가 함께 일치하는지 확인한다. 프런트엔드는 가짜 API가 아니라 가능한 한 실제 테스트 API를 호출해 계약과 사용자 흐름을 함께 확인한다.

6. **전체 회귀 검사**
   기존 전체 테스트를 실행하고, schema snapshot과 상태 전이 검사를 포함한다.

7. **Compose와 브라우저 smoke 검사**
   이미지 빌드, `docker compose config`, 세 서비스 기동, readiness, 브라우저 첫 화면, fixture 한 건 표시, 로그 오류 여부, 정상 종료를 확인한다.

8. **실제 모델 검사(모델 변경 시)**
   Linux GPU 환경에서 고정 평가 음성으로 STT/diarization/화자 점수를 측정한다. 모델·전처리·임계값 변경이 없으면 매 변경마다 실행할 필요는 없다.

9. **증거 기록**
   PR 또는 변경 기록에 실행한 명령, 결과, 생략한 검사와 이유, 수동 확인 내용을 남긴다.

### 16.2 기본 검증 명령 계약

실제 도구 선택 후 `pyproject.toml` 또는 `Makefile`에 아래 의미의 명령을 고정한다. 개발자와 CI가 같은 진입점을 사용해야 한다.

```text
check-format     Python/TypeScript 코드 포맷 검사
lint             백엔드/프런트엔드 정적 규칙 검사
typecheck        Python/TypeScript 타입 검사
api-schema-check FastAPI OpenAPI와 프런트엔드 API 타입 동기화 검사
test-unit        외부 모델 없는 백엔드 단위 테스트
test-frontend    React 컴포넌트와 사용자 동작 테스트
test-integration 임시 DB/디렉터리와 가짜 어댑터 통합 테스트
test-e2e         실제 브라우저의 핵심 사용자 흐름 테스트
test             unit + frontend + integration 전체 회귀
compose-smoke    세 서비스 기동과 health/fixture/browser smoke
model-eval       실제 GPU/모델이 필요한 명시적 평가
```

첫 구현에서 명령 실행기는 하나만 선택한다. 같은 목적의 shell script, Makefile, task runner를 중복해서 만들지 않는다.

### 16.3 테스트 층별 책임

| 층 | 항상 외부 모델 사용? | 검증 내용 | 실행 시점 |
|---|---:|---|---|
| 백엔드 단위 | 아니요 | 설정, 상태 전이, 해시, 경로, schema, threshold 규칙 | 모든 변경 |
| 프런트엔드 단위 | 아니요 | loading/error/empty 상태, 폼 검증, 화자 선택과 저장 동작 | 관련 UI 변경 |
| 통합 | 아니요 | scanner-worker-DB-artifact-API 연결 | 모든 변경 |
| 브라우저 E2E | 가짜 어댑터 | 대시보드→화자 검토→수정→요약 요청의 사용자 흐름 | 병합 전 |
| Compose smoke | 가짜 어댑터 기본 | 세 컨테이너, proxy, 볼륨, health, 오디오 재생, 종료 | 병합 전 |
| 모델 평가 | 예 | STT 정확도 경향, diarization, 화자 오탐 | 관련 모델/설정 변경 |
| 실제 인수 | 예 | Syncthing부터 사용자 수정·요약까지 | 릴리스 전 |

### 16.4 비결정적 AI 결과의 검증법

- 분류와 요약의 일반 테스트는 녹화된 모델 응답 또는 가짜 어댑터로 구조와 흐름을 검증한다.
- 실제 모델 평가에서는 문장 전체 일치 대신 필수 사실 보존, 허용 범주, schema 유효성, 금지된 환각 항목을 검사한다.
- 프롬프트, 모델, temperature, schema 버전을 결과 메타데이터에 기록한다.
- temperature는 분류·요약 모두 가능한 낮게 설정한다.
- 평가 fixture와 기대 기준은 버전 관리하되 실제 개인 음성은 동의 없이 저장소에 넣지 않는다.

### 16.5 Definition of Done

각 기능은 다음을 모두 만족해야 완료다.

- 관련 인수 기준이 명시되어 있다.
- 정상 경로와 대표 실패 경로가 자동 테스트에 있다.
- 중복 실행과 재시작 시 결과가 정의되어 있다.
- 로그에 recording/job 상관관계가 있다.
- 생성/수정되는 artifact와 무효화 대상이 문서 또는 코드에 반영되어 있다.
- 프런트엔드 기능이라면 loading, empty, error, success와 키보드 조작을 확인했다.
- API 변경이라면 OpenAPI 계약과 프런트엔드 타입이 함께 갱신되었다.
- 전체 회귀, 핵심 브라우저 E2E, Compose smoke가 통과한다.
- 모델 동작을 바꿨다면 고정 평가 자료의 전후 결과가 기록되어 있다.
- `.env.example`과 사용자 운영 방법이 실제 동작과 일치한다.

## 17. 인수 시나리오

### A. 입력과 중복

1. **정상 신규 녹음**: 새 m4a가 한 번 등록되고 최종 결과가 생성된다.
2. **복사 중 파일**: 크기가 변하는 동안 등록되지 않고 안정화 후 등록된다.
3. **같은 내용, 다른 이름**: 녹음 레코드와 STT가 중복 생성되지 않는다.
4. **손상 파일**: worker가 죽지 않고 해당 녹음만 조치 가능한 실패로 표시한다.

### B. STT와 화자

5. **단일 화자**: 시간순 transcript와 한 임시 화자가 생성된다.
6. **여러 화자**: 임시 화자별 대표 클립과 segment가 생성된다.
7. **처음 보는 화자**: 자동 확정되지 않고 검토 화면에 나타난다.
8. **알려진 고신뢰 화자**: 임계값과 margin을 만족하면 자동 연결된다.
9. **애매한 화자**: 1위 점수가 높아도 margin이 부족하면 검토로 간다.
10. **화자 수정**: 개별 segment 수정 후 transcript와 요약이 최신 정보로 재생성된다.

### C. 분류와 요약

11. **회의 자동 요약**: 회의로 분류되면 범주 요약 폴더에 결정/할 일 구조로 저장된다.
12. **일상 대화 수동 요약**: 자동 정책에 없다면 요청 전 파일이 없고 요청 후 생성된다.
13. **범주 수정**: 사용자가 범주를 바꾸면 새 범주 경로가 안전하게 반영된다.
14. **깨진 LLM 응답**: 허용되지 않은 결과가 저장되지 않고 재시도/실패가 명확하다.

### D. 운영과 복구

15. **worker 강제 종료**: 재시작 후 stale 작업이 회수되고 artifact가 중복되지 않는다.
16. **Compose 재시작**: 기존 완료 항목은 다시 STT하지 않고 새 입력만 처리한다.
17. **잘못된 환경 설정**: 필수 경로/토큰/범주 오류가 시작 시 구체적으로 보고된다.

### E. 프런트엔드 사용자 흐름

18. **화자 검토 GUI**: 사용자가 대표 클립을 듣고 기존/새 인물을 연결하며 여러 발화를 한 번에 수정할 수 있다.
19. **동시 수정 충돌**: 오래 열린 화면에서 저장하면 409 안내가 나타나고, 사용자 확인 없이 최신 데이터를 덮어쓰지 않는다.
20. **브라우저 접근과 복구**: 키보드로 핵심 검토 흐름을 수행할 수 있고 API 연결이 끊기면 갱신 실패와 재시도 동작이 보인다.

각 시나리오는 입력 fixture, 사전 조건, 실행 절차, 기대 DB 상태, 기대 파일, 기대 로그 이벤트를 표 형태의 테스트 명세로 구현 단계에서 구체화한다.

## 18. 주요 설계 결정과 트레이드오프

### SQLite와 단일 worker

한 장비에서 GPU 작업을 순차 처리하는 현재 목표에는 가장 단순하고 복구하기 쉽다. 여러 GPU/사용자와 높은 동시성이 실제로 필요해질 때 PostgreSQL과 외부 작업 큐를 검토한다.

### Markdown과 JSON 동시 저장

Markdown은 바로 읽을 수 있지만 재처리용 정밀 정보가 부족하다. JSON을 기준 데이터로 두면 화자 수정과 렌더링을 안전하게 반복할 수 있다. DB만 두는 것보다 복구와 이동도 쉽다.

### 화자 식별을 보수적으로 자동화

사용자가 몇 번 라벨링하면 편의성이 커지지만, 다른 사람을 잘못 확정하는 비용이 수동 검토 비용보다 크다. 따라서 절대 임계값과 후보 간 margin을 함께 사용하고 실제 데이터로 보정한다.

### React 기반 별도 프런트엔드

화자 클립을 반복해서 듣고, 여러 후보와 발화를 비교하며, 수정 결과를 저장하는 흐름은 서버 렌더링 폼만으로도 만들 수 있지만 상호작용이 복잡해질수록 화면 상태와 revision 충돌 처리가 불명확해진다. React와 TypeScript를 별도 프런트엔드로 두어 이 사용자 작업을 명시적으로 관리한다. 다만 전역 상태 관리, 디자인 시스템 패키지, 실시간 소켓, 파형 편집기는 실제 필요가 생길 때까지 도입하지 않는다.

### 모델 어댑터와 가짜 구현

추상화 목적이 아니라 느리고 비결정적인 모델을 제외하고 파이프라인을 일관되게 검증하기 위한 경계다. 첫 버전에서 다수 공급자 구현은 만들지 않는다.

## 19. 구현 중 확정해야 할 값

아래 항목은 구조가 아니라 실제 장비와 표본에 따라 달라지므로, 임의의 숫자를 설계 단계에서 확정하지 않는다.

- GPU VRAM에 맞는 WhisperX batch size와 compute type
- `SPEAKER_AUTO_MATCH_THRESHOLD`
- `SPEAKER_MATCH_MARGIN`
- 대표 클립의 최소 길이와 개수
- 실제 운영 범주별 판정 기준과 자동 요약 대상
- 외부 또는 로컬 LLM 공급자와 모델
- 원본 녹음의 처리 후 이동 여부와 백업/보관 정책

이 값들은 9단계 실제 환경 인수 시험에서 측정 결과와 함께 결정하고 `.env.example` 또는 운영 문서에 반영한다.

## 20. 첫 구현의 권장 착수점

가장 먼저 실제 WhisperX를 실행하는 대신, 0~2단계를 한 묶음으로 구현한다. 즉 Compose, DB, 입력 감지, 작업 상태, 가짜 STT/분류/요약, 결과 파일 생성, 최소 대시보드와 상세 화면을 먼저 끝까지 연결한다. 이 수직 흐름이 통과하면 실제 모델은 기존 경계에 연결할 수 있고, 이후 오류가 모델 문제인지 파이프라인 문제인지 분리할 수 있다.

첫 번째 구현 마일스톤의 결과물은 다음이면 충분하다.

- `docker compose up -d`로 `web`, `api`, `worker`가 함께 시작된다.
- 브라우저에서 React 웹 앱을 열고 API 상태를 확인할 수 있다.
- fixture m4a 하나를 입력 폴더에 넣으면 가짜 transcript와 요약이 생성된다.
- 대시보드에서 fixture를 선택해 transcript와 처리 결과를 볼 수 있다.
- 같은 파일을 다시 넣어도 작업이 늘지 않는다.
- worker를 중간에 종료해도 다시 시작하여 완료한다.
- 자동 테스트가 이 흐름을 매번 같은 방식으로 검증한다.

이 기준을 통과한 다음 실제 WhisperX/pyannote와 완전한 화자 검토 화면을 순서대로 붙인다.
